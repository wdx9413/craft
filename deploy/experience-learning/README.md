# Continuous learning worker

The bundled worker polls the Knowledge Source and Experience queues:

1. rotate through registered, active, verified, read-only Knowledge Sources and re-ingest their current files;
2. let the existing source-backed Evidence and promotion policy invalidate drifted Claims and promote only current, conflict-free Claims with enough independent support;
3. for each bounded batch of unclassified candidate or reviewed project Claims, read the project's Knowledge scenario taxonomy and issue a purpose-bound model ticket; classification adds taxonomy references without changing the Claim's review status;
4. call the classifier with the Claim and body-free taxonomy, reusing stable fine/coarse keys or proposing concise new keys; uncertain results remain unclassified, and only keys/references plus a result digest are persisted;
5. list ready `workflow_evolution` model tickets from the mounted `craft-mcp`;
6. read the exact request and sanitized, pinned observations;
7. call the profile's provider using the existing Craft model gateway and an environment-only credential;
8. accept only read-only assertions or coverage gates supported by the Craft Workflow executor, then submit the candidate through `craft_experience_procedure_submit`;
9. automatically queue the candidate's first Shadow dispatch;
10. invoke Craft's local evaluator for pending read-only Workflow dispatches and continue through Shadow, Held-out, automatic Signoff, and Canary when a project scenario contract is configured.

`component-context-daily` starts and supervises the combined Knowledge and Experience worker. The standalone `component-knowledge-daily` and `component-experience-daily` products start the same worker in a single-domain mode, so each worker calls only tools exposed by its mounted product. A process-level lock under `$CRAFT_DATA_DIR/runtime/` ensures only one active worker owns each learning component per data root, even when multiple MCP sessions start concurrently; the combined Context worker reserves both Knowledge and Experience. Memory promotion runs synchronously during stable-fact capture and does not need a polling worker. Set `CRAFT_CONTINUOUS_LEARNING=0` to disable automatic startup. `CRAFT_EXPERIENCE_POLL_MS` controls Experience polling from 1 second to 5 minutes; `CRAFT_KNOWLEDGE_POLL_MS` controls Knowledge re-ingestion from 1 minute to 1 hour (default 5 minutes). The standalone `craft-continuous-learning-worker` command remains available for deployments where a separate process owns the loop; do not run it alongside an active component MCP loop for the same data root. Knowledge sync state is content-free and stored at `$CRAFT_DATA_DIR/knowledge/learning-worker-state.json` (default `$HOME/.craft_data/knowledge/learning-worker-state.json`). The loop scans at most five Sources per Knowledge pass and rotates fairly; each Source is bounded by the existing 10,000-file and 20 MB ingestion limits. Partial Sources retain a digest-pinned page cursor in that central state file, resume from that page after a restart, and restart at page one if the Source revision invalidates the cursor.

The worker never stores model prompts or responses. A model response is only a candidate. Codex plugin deployments set `CRAFT_LEARNING_MODEL_HOST=codex-cli`; with no active Codex Profile, the worker creates a deterministic purpose-specific Profile for `gpt-6-luna`, without an API credential. The Host transport uses `codex exec --ignore-user-config --ephemeral --sandbox read-only --skip-git-repo-check --json`, caps output and time, and permits at most one model call per poll. Knowledge classification and Evidence review pass a strict JSON Schema through `--output-schema`; the schema exists only in a private temporary file deleted after the call. It starts no CLI process when the matching queue is empty. For Knowledge classification, the exact model ticket is completed with a digest after either saving keys to the candidate Claim and project taxonomy or recording an unclassified decision. For Experience, the ticket is completed only after the exact candidate linked to it is submitted. A post-response failure records only the ticket ID, input digest, failure stage, safe failure code and timestamp in `$CRAFT_DATA_DIR/knowledge/classification-attempts.json`; the same unchanged input is not sent to the model again. Updated Evidence, taxonomy, model profile or classifier contract produces a new input digest and permits a fresh attempt. Model transport failures before a response remain retryable. API-provider deployments retain the existing credential-backed gateway. Read-only Workflow evaluation is configured in `$CRAFT_DATA_DIR/experience/projects/{project_id}/experience-scenarios.json` (default `$HOME/.craft_data/experience/projects/{project_id}/experience-scenarios.json`). Each scenario may declare pinned `shadow`, `held_out`, and `canary` case sets. Craft verifies each case root resolves to the scenario's project identity, runs the exact pinned Workflow through its read-only executor, stores only boolean step results and digests, and creates Evidence bound to the dispatch. The held-out case set must have its own digest and `independent_of_training: true`. Signoff uses the fixed policy `craft:auto-signoff:all-prior-gates-passed.v1` after Shadow and Held-out pass. Canary also checks that the current release still matches the dispatch's pinned baseline. Only a passing Canary changes `current`.

`craft_context_open` automatically enrolls only the current project's root `README.md`, root `AGENTS.md`, and `.serena/memories` directory as bounded, read-only Sources, then ingests a newly enrolled Source once. The worker re-ingests active `verified` or `bounded`, read-only Sources on its normal schedule and never writes into project files. A bounded Source produces review candidates, but its unverified Evidence cannot satisfy automatic promotion. Source descriptors, ingestion receipts, Claims, Evidence and worker state stay under Craft's central Knowledge data root; Memory and Experience continue using their own tier directories. Worker output contains a one-way digest reference, counts, and statuses rather than source identifiers, source bodies, or local file paths.

The automatic evaluator supports only linear Workflow assertions (`file_exists`, `json_value`, and `coverage_gate`). It does not run arbitrary shell commands. Missing or invalid scenario configuration leaves the dispatch awaiting an evaluator; Graph and Prompt candidates still require an external adapter. Memory's session/project/global capture and promotion run when the Host captures a classified fact; Hooks are optional. This learning loop does not copy conversation content or bypass Memory conflict and tier rules.

The example deployment contract is [adapter.example.json](adapter.example.json). It contains no credentials or real reviewer/test-set references. Local protocol acceptance is `./scripts/experience/acceptance.sh`.

Each worker-to-MCP request is bounded by `CRAFT_LEARNING_MCP_REQUEST_TIMEOUT_MS` (default 60 seconds, maximum 5 minutes). Knowledge held-out adjudication now runs the bounded Codex CLI call inside the MCP service; that one request has a 135-second minimum to accommodate the Host's 120-second deadline. The service re-reads current Claim and held-out Evidence, records its own Trace, and rejects caller-supplied decisions. A per-case process lock prevents simultaneous Host calls. If a request stops responding, the worker rejects pending calls and stops its MCP child so the supervised process can exit and release its component locks.

After a valid model response, the service stores a content-free recovery result in the case's Knowledge partition before finalizing the Trace and evaluation case. A later process can resume those writes without calling the model again. A process exit between the model response and this durable result remains ambiguous because Codex CLI provides no reusable call receipt; the retry policy cannot claim exact-once model execution for that interval.
