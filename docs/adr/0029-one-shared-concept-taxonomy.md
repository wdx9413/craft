# ADR-0029：Knowledge、Memory、Experience 共用一个概念分类

状态：Accepted

## 决策

Knowledge、Memory 与 Experience 不再各自定义"记录类型"。三者共用一个
`craft-common-ontology` 分类，每条持久记录必须落在六个概念之一：`fact`、
`rule`、`decision`、`term`、`preference`、`procedure`。每个概念都带一条
判定标准和一个反例；写入时用同一套校验，拒绝空泛词、依赖上下文的指代和
超过 300 字符的散文，要求记录能独立读懂。

各子能力保留自己的存储、治理与评测流程，只把"这条记录是什么"统一。旧的
组件内类型通过显式映射表落到新分类（`failure_mode` → `rule`，`procedural`
→ `procedure`，`scenario` → `procedure`），映射表之外的值直接拒绝，不猜。

## 原因

此前三套局部类型互不相通，同一句"这个项目用 pnpm"可以合法地写成 Knowledge
的 `fact`、Memory 的 `preference` 或 Knowledge 的 `rule`。类型多不是问题，
缺少"什么算事实、什么算约定、什么算偏好"的判定才是问题：写入方按自己方便
挑类型，读取方拿到的是无法复用的散文。分类放在 `craft-common` 而不是新建
第五个子能力，是因为它本质是三者共享的词汇约束，做成独立能力只会让三者
都多依赖一层转发。

## 代价与后果

- 写入变严：不合规的语句会被拒绝，写入方必须改写或换类型。这是有意的，
  否则脏数据只会在读取时反复付出解释成本。
- 历史数据不回溯改写；校验只拦新增写入，旧记录按原样保留并可按映射表读取。
- 六个概念是封闭集合。新增概念需要修改共享包并重新发布，不能由某个子能力
  私自扩展，否则分类会重新碎片化。
- 300 字符上限意味着长材料必须放进文档再被引用，而不是塞进账本。这符合
  "正文归调用方、Craft 只持引用"的既有边界。

## 非目标

- 不建立通用知识图谱、本体推理或自动实体抽取。
- 不改变 Knowledge、Memory、Experience 各自的评审、证据和发布门禁。
- 不把 `CONTEXT.md` 的术语表与账本记录自动同步；`term` 类型只保证格式一致，
  是否登记进术语表仍由人决定。
