# hook 属于流程，不属于某次写入

hook 不是"写后回调"，而是流程上的扩展点，因为流程在工作的**两侧**都有要紧阶段：某条规则必须在工具调用**之前**看到它才能拦住，某条经验必须在任务结算**之后**写才有价值。八个阶段按流程顺序固定（`turn_start`、`context_resolve`、`capability_discover`、`permission_check`、`tool_before`、`tool_after`、`task_settle`、`turn_end`），`order` 只在阶段内决胜、不能跨阶段把自己提前，因此"累积先于演进"是可检查的而不是注释。三条安全规则：**只有 gating 阶段（`permission_check`、`tool_before`）可以拒绝**——两者都站在某个效果前面，别处 `denied` 无物可拒，属于契约违反并在装配期拒绝；**一次拒绝停止该阶段**；**抛出的 hook 记为 `unobserved` 而不是失败**，因为累积是侧信道，坏掉的 hook 不能改变它所观察的工作的结果。hook 同时是**单点能力埋点**的载体，因此它必须带能力归属：`buildCapabilityRegistry` 在装配时填入 owner，`PhaseResult.outcomes` 同时给出 `capability` 与 `hook`，每次 phase 结论落一条**无内容**记录，键为 `(phase, capability, hook)`。相应地 `HookContext` 的 `scope_kind` / `scope_id` 是可选的——一个名字不出 scope 的阶段不该编一个出来（MCP `tools/call` 边界上，一次调用未必绑定任务），而为了满足必填字段而发明 scope 会让埋点记录本身失真。
