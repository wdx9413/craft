# Mod 是受信任的运行时扩展模块

状态：Accepted

Craft 中的 Mod 是可执行运行时模块，可在声明的内核和界面扩展点注册 Hook、命令及界面贡献；Hook 是 Mod 注册的事件处理合同。Mod 可介入审批决策点，人工创建并获信任的 Mod 可在用户授权的范围内使用审批策略能力。自进化生成的 Mod 永远不能声明或调用审批策略能力，也不能批准自身或扩大权限。用户可逐个审查并信任 Mod，或信任当前已审查集合；信任绑定精确代码与权限声明版本，任一变化都要求重新审查。分发 Plugin 是包格式，不等同于 Mod 本身；旧 `mod` 稳定键中的文本认知约束归类为 Rule。

Mod 通过版本化事件合同接入所有已声明的 Craft 内核与界面插入点，包括输入、Context、模型请求、工具调用、审批、任务/资产、渠道和界面事件。事件处理器可按声明观察、修改、拒绝或受控接管事件；权限以贡献项声明并由 Runtime 执行。无界面 Host 明确不支持界面贡献，未实现的事件不宣称兼容。事件处理器可以在审批节点调用已获授权的策略能力，但不能通过绕过事件合同直接篡改内核授权状态、最终出站检查或审计记录。

自进化可以提出可执行 Mod 候选并运行代表性回归；自动生成或回归通过不构成执行信任。自进化 Mod 的能力白名单排除审批策略能力，且不能通过“信任全部”解除该类别限制。其它声明能力只有在用户信任该代码/权限版本后才可运行；用户对其赋予的能力范围按明确声明生效。自动推广仍须逐级回归与可撤销发布。

## 后果

- 需要维护 Mod API、版本化事件目录、Host/平台兼容矩阵、能力声明、信任回执、加载/卸载及运行结果证据。
- 模块可以在审批决策点运行；权限策略保持为受控接口，不暴露任意核心内存或授权状态写入。
- 自进化 Mod 与人工信任 Mod 使用不同的能力上限；来源类别必须由 Runtime 记录，不能由 Mod 自报。
- 安装或发现 Mod 不等于信任或加载；代码或权限声明变化使旧信任失效。
- 当前文本型 Mod Registry 不能代表上述可执行运行时模块已经实现；旧文本规则必须保留兼容映射但不得伪装成 Mod Hook。
