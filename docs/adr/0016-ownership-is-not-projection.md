# 能力的归属不是它的产品投影

`CraftCapability.owns` 回答"谁实现了它"，必须为真，因此故意写窄；`component-*` MCP surface 回答"加载这个产品的宿主能看到什么"，可以比归属更宽。两者故意不同，而且这个差异本身是有用的信号：早期 knowledge 包尚未声明 Claim 与 Wiki 写入归属；当前 Claim 已由 Knowledge 包的 `KnowledgeClaimGovernance` 实现并装配，`owns` 已匹配 `craft_knowledge_claim_*`。Wiki 写入仍由 core 门面提供，产品投影可以包含它，不能据投影反推实现归属。**一个产品必须暴露它的能力所装配的东西**：实测出两处违反，都已修——`component-experience` 的旧字面量匹配不到任何 `craft_experience_ledger_*`，使经验账本（experience 的写入侧）无法通过以它命名的产品访问；`component-knowledge` 匹配不到 `craft_project_*`，而 knowledge 包七个内核里有两个服务这些工具。两处都因为没有东西可检查而长期无人发现，所以现在投影由能力声明的族推导，并有测试断言"`owns` 匹配到的每个工具都在投影里"。`component-context` 仍组合**冻结的**旧名字空间：它是较旧、较窄的投影，其成员资格是兼容面，为与它无关的理由改变既有宿主看到的东西不是清理。`context_resolution` 与 `retrieval_adapter` 由两个投影共享、不属于任何能力，因为只装一个关注点的宿主仍然要能解析那个关注点持有的材料。`owns` 还必须匹配真实存在的工具，否则一次改名留下正则不会有人报出来。
