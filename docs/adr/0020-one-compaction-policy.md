# 压缩只有一套策略

`compact()`（`src/compaction.ts`）是 Craft 回答"预算里能装什么"的唯一实现。此前有三套互不知情的机制：`compactConversation`（保留首条 system 与一段**连续**的近期后缀到预算 65%，省略中段）、`ReversibleContext.project`（按**权重再新旧**整段淘汰并报出被省略的 id）、`compactionPlan`（把约束**移出淘汰竞争**再按权重排序）。它们在要紧处不一致：两套按权重排序却把并列项朝**相反**方向决胜，且只有一套保护任何东西——于是调用者拿到什么取决于它碰巧调了哪个函数，而不是取决于谁选定的策略。

合并后的策略有两个阶段，而且**故意**不是同一个填充规则：**保留阶段**（`tail_share`）取一段连续后缀，遇到装不下的就停——连续性正是被省略的跨度可以被打包成一段来描述的前提，这是 transcript 需要的规则；**竞争阶段**按权重打包，装不下就跳过并试下一个——这才是把预算用满。决胜项现在只有一个：**权重降序、再新者优先**。"偏好较新"对两类调用者都是可辩护的默认（当前子目标优先于旧的），并且它改变了 `compactionPlan` 在权重并列时的输出——那是合并的自觉后果，由测试记录。

保护是**减法**而不是更高的权重：`protect` 把段落同时移出预算与 omitted 集合，其成本**单独**报告（`protected_tokens`、`total_tokens`）。给它一个大权重仍会输给更紧的预算，而那正是治理研究测到的失效模式——压缩为任务连续性而设计，把常驻政策当作可淘汰内容。一条保护 id 没有匹配到任何段落会被报为 `unbound`，所以配置错误可见而不是静默地什么也没保护。`compactWithPromotion` 是另一条独立的保证：它把目标段**抬到所有段之上**，于是它仍然缺席的唯一理由就是根本装不下；装不下就抛错，因为"恢复"若返回一个不含该段的投影，就与成功无法区分。
