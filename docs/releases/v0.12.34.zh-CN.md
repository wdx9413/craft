# v0.12.34：统一 Harness、任务闭环与单点能力评测

## 本版收口

Craft 在本版把产品概念落成可校验契约：

```text
Agent = Model + Harness
Harness = Context + Tool + Permission + Environment
Environment = Sandbox + Runtime
Context = History + Knowledge + Memory + Experience + State
```

`Hook` 是贯穿上述边界的生命周期扩展点，不是 Harness 的第五个组成面。Hook 只能观察、补充 Evidence、请求暂停或阻断策略不允许的动作，不能绕过权限、篡改 Receipt 或建立第二套账本。

任务型运行统一使用：

```text
Goal → Target → Task Contract → Plan → Step → Accept → Outcome
```

普通对话使用 `turn` 模式，不强制创建完整任务；需要执行、写入、验收、恢复或学习时进入 `goal/plan/execute/verify/learn` 模式。

## 已实现的核心机制

- `VerifiedWorkLoop` 保存交互模式、Target、Plan、Step 和 Accept 的可复现摘要，并继续复用现有 Task、Receipt、State Snapshot、Acceptance 和 Outcome 账本。
- `EvaluationContract` 统一单点能力的阶段：`mechanism_passed → fixture_passed → conformance_passed → integration_passed → host_verified → business_eligible → routeable`。阶段只能前进，单元测试或 MCP 握手不能单独使能力进入默认路由。
- Hook 新生命周期点通过兼容映射接入既有 HookPlane，不破坏旧组件和既有 Trace。
- 产品版本由 `src/version.ts` 统一提供；Schema、MCP Protocol、Adapter 版本独立表达，发布门禁覆盖组件包、插件 manifest 和 Marketplace。
- Knowledge 默认按本机自动晋升策略处理：来源、Evidence、scope、有效期和正文引用完整，且至少有两条独立 Evidence/Observation 才提升当前 Claim；同一段聊天或同一 Evidence 的重复提交不累加。旧导入、来源缺失、过期或冲突的 Claim 留为 `revalidation_required`，不会因为旧 Markdown 描述进入 Host Context。人工只作为可选例外或阈值调整，不是默认审核瓶颈。
- 离线知识迁移补充 provenance rebind：它逐页核验 Markdown digest 后恢复旧 Candidate 的 Claim→Source 关联，但不改变 candidate 状态、正文或 Evidence confidence。
- 旧知识新增显式模型复核入口：审核结论绑定 Candidate 与源 Markdown digest；通过项恢复完整脱敏正文并只获得 bounded Evidence，不能冒充当前线上事实。共享内容进入 global，项目内容绑定精确 project scope，无法识别项目的内容留在 `project:unbound`。
- Memory 支持用户显式陈述的受限捕获、topic 冲突和 `supersede` 替代链；working/episodic 的默认有效期不会把短期状态伪装为长期偏好。
- 三个单点产品补齐为可独立使用的最小闭环：Knowledge 可登记来源并草拟/复核 Claim；Memory 可 materialize 后按显式 scope 读取或列表查看、处理冲突和维护；Experience 可从两条独立 Observation 生成 Workflow 或 Graph Procedure Candidate。它们均不复制 Core 的 Evidence、Policy、Context Receipt 或执行账本。
- Experience 的 Graph 是候选资产而不是第二个执行器：支持条件边、并行汇合、人审恢复、补偿和有上限的重试；依赖关系仍保持 DAG，普通反馈循环必须带 `retry` 上限或 `human_resume` 批准。Graph 固定为 `draft` 且 `automation_authority: false`，仍需 Shadow、held-out、Signoff、Canary 后才能由 Core 路由。
- Decision-point Context Gate 在高杠杆动作前解析最小受管 Context；连续无状态变化的 running 观察达到配置阈值后，Verified Work Loop 转为 `needs_replan`，不继续把“仍在运行”当作进展。
- 三个独立组件现在拥有 Codex 生命周期桥接：`UserPromptSubmit` 只注入本组件的受限 Context 和 Resolution Receipt；`craft-memory` 仅接受 `记住：…` / `/remember: …` 的显式同意写入；`craft-experience` 只从“修改 + 本地验证”的脱敏工具元数据形成 Observation。Hook 失败始终 fail-open，且只有用户信任插件后才会实际运行。

## 本机迁移验证

本机旧知识源共识别 53 条可迁移页面。它们已逐条完成 source digest 绑定与受限模型复核，53 条均进入 `reviewed`，并恢复完整 Markdown 正文；复核记录明确要求涉及当前系统状态时重新求证。当前 scope 分布中 12 条为 global，其余绑定精确项目；10 条因旧页面没有稳定项目标识留在 `project:unbound`，不会被默认 Context 路由。

该结果证明迁移、来源链和审核机制可运行，不证明 53 条历史内容在今天仍然成立，也不证明 Codex Host 已在真实任务中稳定召回它们。

## 边界

本版仍默认单 Agent。真实模型、真实 Host、企业凭据、跨平台强隔离和业务 Case 的效果必须由部署方显式配置并通过真实评测；未配置时返回 `unavailable`，不会伪造成功。多 Agent/A2A 仍是受控 Adapter，不自动进入默认路由。本机数据库目前仍没有真实 `memory_ledger`、`work_loop` 或 `host_run` 业务记录，因此 Memory 自动形成与长任务可靠性仍属于“机制已实现、真实接线待证明”。
