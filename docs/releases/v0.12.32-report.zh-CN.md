# v0.12.32：Runtime Assurance & Learning Loop

## 这一版解决什么问题

v0.12.32 把 Task、Capability、Host、State、Trace、Acceptance、Evaluation、Memory、Knowledge 和 Workflow Evolution 接到同一条可恢复闭环。Craft 负责事实、边界、回执、再观察、验收与演进；Host 仍负责模型和工具执行。

统一闭环为：

```text
Task Contract → Activation Profile → Preflight → Host Dispatch
→ Action Contract → Receipt → State Snapshot → Re-observation
→ Acceptance → Outcome → Trace / Evaluation → Candidate Evolution
```

## 新增与补齐

- 新增 `TraceReviewKernel` 与 `craft_trace_review*` MCP：根据不可变 Trace 生成 `passed`、`needs_attention` 或 `inconclusive`，定位首错、根因和版本指纹，不把模型自述当作完成证据。
- 新增 `MemoryMaintenanceKernel` 与 `craft_memory_maintenance_*` MCP：Light、Review、Deep 三阶段只生成脱敏候选；记录去重、缺正文引用、敏感来源、孤立语义记忆和使用信号，不自动删除、覆盖或发布。
- 新增 `RuntimeProofKernel` 与 `craft_runtime_proof_*` MCP：把 manifest、probe、conformance、attestation 和 checkpoint rehydrate 接成一条环境证明链；环境漂移、未验证隔离和不受支持的高风险 Windows 写入失败关闭。
- 新增 owner-scoped `McpTaskKernel` 与 `craft_mcp_task_*` MCP：异步 Task 先持久化，支持 `working/input_required/completed/failed/cancelled/expired`、TTL、取消和幂等；正文只以 digest 留存。
- 新增 `craft_memory_maintenance_cycle`：按稳定游标批量消费终态 Trace，写入不含正文的学习观察；重复运行幂等，观察结果仍需 Evidence、评测和 Signoff 才能进入记忆或 Workflow。
- 新增 `craft_runtime_model_status` / `craft_runtime_model_probe`：读取模型配置的无密钥状态，并以一次有界请求验证可达性。未配置密钥、未注入 Transport 或上游失败统一返回 `unavailable`，不把探测当成质量结论。
- 统一 MCP 核心面暴露 Trace Review、Memory Maintenance；完整面保持兼容，核心状态仍由同一 SQLite 账本维护。
- 运行时监督事件支持 `notify`、`question`、`steer`、`approve`、`pause`、`abort`、`resume` 等受控动作。
- 版本、插件清单、Claude/WorkBuddy/DeepSeek 适配器和测试断言统一到 `0.12.32`。

## 已验证范围

- Trace Review：终态、首错、Policy 根因、未知根因、缺失观察、幂等冲突和证据引用。
- Memory Maintenance：默认阶段、三阶段扫描、使用信号、重复运行、冲突、候选不发布和敏感来源检查。
- MCP：核心面可发现并调用新增工具。
- v0.12.32 专项新增模块行、函数、分支覆盖率：100%。

## 边界与未宣称能力

本版的真实 Codex/Claude、外部凭据 Broker、企业隔离器、对象存储和远程 A2A 仍通过 Adapter 接入；未配置时返回 `unavailable` 或失败关闭。Fixture 只能证明机制，不证明真实业务质量。Memory/Knowledge 的后台维护仍是候选生成，必须继续经过 Evidence、Evaluation、Signoff、Canary 和精确回滚，不能自动改写生产 Skill 或 Workflow。

模型探测只证明“当前凭据和网络能够得到响应”，不证明模型质量、工具调用正确性或业务效果；真实质量仍由固定 Case、同环境、等预算和重复 Trial 的 Eval Campaign 证明。
