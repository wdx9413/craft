# Experience：产研流程的多入口、多出口与返工设计

状态：设计已落地到版本化配置与 Invocation；2026-10-04。实现与验收见 [交付记录](component-versions-graph-implementation-2026-10-04.md)。此文保留设计背景；当前能力和限制以交付记录为准。

## 结论与配置组织

用户确认的业务层级：**互联网产研是场景，需求研发、Bug 修复、只做诊断、Code Review 是子场景。** 场景管理共享流程定义和规则；子场景按任务意图、已有材料选择合法入口、路径策略与目标出口。术语统一为“场景 → 子场景 → 入口/路径/出口 → 运行实例”。

配置分为以下内容，先作为同一个版本化定义包内的结构，不要求各建独立存储或文件：

1. **场景配置**：互联网产研的业务范围、共同规则、共享 Workflow/Graph 与子流程引用，以及子场景集合。
2. **流程定义**：节点、命名入口、出口、转换条件、输入输出契约、验收、允许的副作用、失败处置。保留版本与定义摘要。
3. **子场景配置**：任务目标与匹配条件、必需材料、允许的入口及目标出口、路径策略、参数、预算和权限约束。只选择定义允许的路径、缩小权限，不能通过任意配置覆盖跳过验收或扩大权限。
4. **运行实例**：一次具体任务选择的场景/子场景、入口与目标出口，以及本次输入与材料版本、当前节点及尝试次数、已验收产物、决策/派发/回执、未决问题。实例之间不共享可变状态。

一份互联网产研场景配置下包含多个命名子场景条目，共用流程节点和子 Procedure，不为每个入口复制整份流程。是否拆文件属于存储组织；团队或业务的输入输出、验收和治理方式显著不同时，再拆独立流程并引用共享子 Procedure。现有 ScenarioSignature 用于归类观察，不应直接当作可执行的场景或子场景配置。

子场景与入口不强制一一对应：Bug 诊断和 Bug 修复可以共用 bug 入口，按目标出口和后续路径区分；需求研发可以声明“从需求开始”和“从已确认方案开始”两个合法入口，后者仍须提供前置材料与证据。入口是起点，子场景是本次要完成哪类工作。相同入口在不同子场景下可以选不同路径，回退也只能走该子场景允许的边。若匹配多个子场景且会改变目标或权限，需明确范围后再绑定运行。

## 产研示例

| 子场景 | 命名入口 | 核心路径 | 目标出口 |
| --- | --- | --- | --- |
| 需求开发 | requirement | 澄清 → 设计 → 实现 → 验证 → 审查 → 整理交付 | delivery_ready |
| Bug 修复 | bug | 复现 → 定位 → 修复 → 回归 → 审查 → 整理交付 | delivery_ready |
| 只查原因 | bug | 复现 → 定位 → 整理诊断依据 | diagnosis_report |
| 只做 CR | review | 检查输入变更 → 审查 → 整理 findings | review_report |

实现/修复、验证/回归、审查和交付可复用同一子流程，以命名参数和输入契约表达差异。入口必须提供所需材料和证据，不意味着入口前的阶段已经完成。选择 review 入口不允许假定需求审核或测试已通过。

一个定义可以声明多个合法出口；一次根运行绑定一个目标交付出口，子调用各有自己的出口。达到中间材料节点不自动结束根任务。修改目标出口需要显式记录范围变化并重新规划，不能为规避失败验收偷偷切换。

诊断报告可以如实记录未复现和未决问题；报告交付完成不等于根因已确定。review_report 可以包含发现的问题，不等于所有问题已修复。delivery_ready 不等于已经部署；真实发布需要独立的 deployed_and_verified 出口、授权和目标环境证据。blocked、failed、cancelled、inconclusive 是运行状态，不包装为成功业务出口。

## 控制流与执行分工

Workflow 用于已选定的步骤序列，Graph 用于运行中依据结果决定分支、返工或并行汇合。两者应共享 Entry/Exit、材料、验收、版本和 Invocation 合同；线性 Workflow 可视作 Graph 的受限形式，不新增第二个执行器。

在当前 Runtime 内增加解释 Graph 下一步的能力，继续复用 DurableActionLoop 派发、AcceptanceGate 验收与 Host Adapter 执行真实动作。配置不存任意可执行代码：条件引用受支持的判定器或已记录的决策。已验证产物、明确的人类决定、真实执行结果才能驱动转换。

分支必须定义命中规则、无匹配或证据未知时的行为。互斥分支出现多个匹配时报告歧义，除非定义中明确配置且验收了优先顺序；不能靠模型临时猜一个。并行分支明确 join 条件、写入互斥和失败传播。当前仅支持独立只读并行，不能由此推断任意写入或子流程都能并发。

## 四种“回退”分别处理

| 操作 | 语义 |
| --- | --- |
| resume | 中断后继续同一运行；已派发但无回执时先核实，不能重复动作。 |
| retry | 在输入和权限仍有效、可安全重试的前提下，再尝试当前步骤；保留旧尝试。 |
| rework | 审查或测试发现问题，沿定义允许的边退回实现/设计等阶段；新产物触发依赖失效与重新验收。 |
| compensate | 对已经发生的外部副作用实施明确的补偿动作；没有补偿合同则停止并交接。 |

Procedure 版本恢复是另一个资产管理操作，不等于当前运行回退。撤销发布、删除工单、还原文件都不能由“回到上一步”自动推导。

返工不是把步骤状态重置为 pending：

1. 持久化返工原因、证据、目标节点、作用范围和剩余预算，创建新 attempt/运行修订。
2. 找出依赖被修改材料的下游产物与验收，使其对新一轮失效；保留原记录供追溯。无关且依赖完全相同的已验证结果可以继续使用。
3. 先处理仍在运行的受影响分支；确认停止或完成、核实副作用后再推进，不能假定取消请求已成功。
4. 新输出使用新材料引用；验收绑定当前输入摘要、代码快照和 attempt。旧分支的迟到回执只能归档，不能完成新一轮。
5. 为每条返工边、每个节点及整个运行设次数/时间/成本限制；连续无进展转 blocked/handoff。人工恢复边也不能绕过总预算。
6. 需求本身变化时重新检查目标与验收；超出原范围的新需求须重新规划，不能作为普通重试处理。

例如：实现产物 code@A 已通过 test@A，审查要求修改后生成 code@B。test@A 和原审查结论不能用于 code@B；重新测试和审查后才能达到交付出口。定义图允许有界环，实际运行记录按尝试追加，不抹除失败历史。

## 与版本能力的关系

运行固定场景配置版本、子场景配置版本（或其在配置包中的摘要）、流程内容版本、子 Procedure 版本/摘要、入口、目标出口、输入引用和验收合同。资产内容版本与审核/启用记录版本应分开表达。更新配置默认影响新运行，旧运行不得静默改变定义；当前实现对版本漂移要求 replan，需要保留这一保护直到显式迁移合同落地。权限撤销和安全性失效仍必须即时阻止后续派发，不能借锁定旧版本继续执行。

对照评估绑定入口与出口、输入快照、Host/模型/预算。不能用 review 子场景通过证明 bug 子场景可用；共享节点变化需要重验所有受影响的子场景路径及回退行为。基线与候选流程版本可以不同，这是被评估的变量，其余比较条件应固定。

## 当前实现与差距

已读取当前工作区代码和测试，以下不代表本次重新执行测试：

- [Procedure composition](../../capability/craft-experience/procedure-composition.ts)已有命名 Entry/Exit、固定 Route、子调用、输入输出验证和独立只读并行声明；`validateProcedureComposition` 明确只接受 workflow，Graph 当前不能直接使用这条组合契约。
- [Invocation](../../core/application/procedure-invocation.ts)经 ProcedurePlanner 将所选 Route 降为持久工作项；已有入口绑定、出口验收、幂等回执、恢复、受限重试和版本漂移保护。当前 resume 恢复对应失败/阻塞项，不是任意退回上游节点并失效下游。
- [GraphCompiler](../../core/graph-compiler.ts)调用 [Graph 校验器](../../core/workflow-dag.ts)处理条件、重试、人工恢复和补偿边，输出声明 `host_dispatch:not_performed`。静态编译通过不能证明运行时条件选择、返工、补偿已经执行。
- [组合测试](../../tests/procedure-composition.test.ts)、[调用测试](../../tests/procedure-invocation.test.ts)覆盖已有固定路径与恢复；[Graph 测试](../../tests/component-procedure-graph.test.ts)覆盖候选生成与协议，不是需求/Bug 多入口动态 Graph 的完整实机验收。

因此，完整需求还需要：共同的 Graph Entry/Exit 合同、场景/子场景配置、运行时条件转换、有界返工及依赖失效、受影响并行分支处理、版本化子场景验收。不能把现有多入口 Workflow 或 Graph JSON 支持描述成这些工作已完成。

## 首批可验证验收

1. 同一互联网产研场景下，根据需求研发、Bug 修复、诊断、CR 子场景选择 requirement、bug、review 等入口；未声明入口、不合法子场景/入口/出口组合及不足输入被拒绝。
2. bug 可交付诊断报告或继续到修复交付；review-only 不执行修改，也不误报发布完成。
3. 审查失败返工到实现，生成新材料，并重跑受影响测试/审查；其他有效材料保持可复用。
4. 同一返工边预算耗尽必须停止；人工恢复不得清零次数。
5. 返工前迟到的测试成功回执不能通过返工后的出口验收。
6. 断线恢复核实原派发，不重复创建副作用；补偿无合同或无权限时显式交接。
7. 子流程未通过其出口验收时，父流程不可消费输出或宣告完成。
8. 配置与定义变化不改变既有运行；撤销阻止继续，迁移需要重新检查输入、权限和验收。

以上应通过标准 Skill + MCP 在同一现有 Runtime 上验收；Workbench 展示运行路径、返工轮次、版本和证据。实施前先固定这些语义，再补编辑器，避免让图形外观掩盖执行缺口。
