# Craft Context 自进化与真实场景记忆：业界一手资料调研

日期：2026-11-19
范围：面向 Codex 插件的知识、记忆、经验、标签与 Notes；只读调研。
方法：先用 AnySearch 检索学术与代码领域（先发现 academic.paper、code.snippet 等子域）；再核对论文原文、官方 OpenAI 文档/文章和作者项目。按要求尝试 Agent Reach GitHub 搜索；渠道返回 `RATE_LIMITED` 后停止重试。检索结果可能有索引延迟，以下发布日期按一手页面记录。

## 结论

Craft 的目标边界是合理的，现有方案也已覆盖不少关键设计：统一 Value Gate、事实/推断区分、领域适配器只作提示、Experience 场景分类、候选评测和撤销等已有 ADR/技术契约。当前最值得补强的不是再造一个“更大的行业本体”，而是把**真实任务经验的摄取、来源和时效、可复用上下文构造、配对评测与运行反馈**变成可追踪的产品闭环，并用真实 Codex Host 运行证据证明它有效。

尤其要分清三层：

1. **价值判断**回答“是否值得留下、暂存为什么类型”。场景不该成为门槛。
2. **语义分类**回答“这条证据属于什么业务对象、任务、环境和时间状态”，允许待分类、后续重分类。
3. **使用/晋级评测**回答“候选是否帮助了目标任务且没造成回归”。分类置信度高不等于经验真实有效；一次任务成功也不等于因果提升。

建议把检索与存储对象从散落的标签，收敛为可审计的“经验证据包”：来源事件与主体、任务/项目/设备/目录/文件作用域、发生时间和有效区间、原始观测与模型推断分栏、关联业务实体/制品、候选与被复用的版本、评测合同/结果、撤销与过期状态。Ontology 负责语义和迁移；不可自改的 Core Policy 负责权限、信任、隐私和安全门槛。

## 对真实世界与业务语义的判断

“编程/办公/科研/旅游”是任务场景视角，不是事实本体，也不应决定是否摄取。真实使用里一条记录可能同时关联：**主体/业务对象**（人、团队、客户、系统、项目）、**任务与目标**、**制品/数据**、**环境**（设备、目录、文件、服务版本）、**时态**（发生、有效、被替代）、**证据与来源**、**动作/结果/验证器**。场景适合做查询路由和评测分层，但业务对象和事件关系才是跨场景复用与核验的骨架。

建议保留分离但可链接的资产：

- **Knowledge / Fact**：可核验的外部状态或业务声明；有来源、观测时间、有效期、可信等级和撤销/冲突关系。
- **Memory**：特定会话/任务/主体/项目中的经历、偏好、计划和未完成事项；可以暂时有效且可被新证据更新。
- **Experience**：从一个或多个实际执行中归纳的做法、失败模式、适用条件与验证器；多次成功是证据，不是经验正文。
- **Notes**：设备/目录/文件等位置和环境的简短描述；应成为 Experience/Procedure 的 scope 元数据，不把文件说明误当通用事实。
- **Ontology / tags**：可版本化的类型、关系和分类结果。标签是解释/检索索引，不是可信度本身；人工确认、工具观测、模型推断要区分字段和状态。
- **Procedure/Mod/Skill candidate**：有明确行为变化和验证器的可执行候选；先隔离评测，不能仅因被总结或用户重复说过就自动启用。

不要把“业务场景标签”作为提取的先验资格。用户明确说“这个目录是生产只读配置，切勿修改”即使尚无 scenario adapter，也应先存为有来源、有 scope 的声明/待验证 Note；其危险操作约束由 Core Policy/审批执行，不能由模型自创高优先级规则。

本节依据仓库内已接受的 ADR 和技术契约审阅；它说明设计与代码边界，不代表已在用户安装的 Codex 插件和生产 Runtime 端到端生效。

|---|---|---|---|
| Value Gate | `craft-common/packages/craft-common-ontology/src/value-gate.ts`；ADR-0034 §2 | 代码是确定性规则/正则的首阶段分类与理由生成，不是事实核验器或完整的语义价值评估。Gate 输出候选/忽略/复核等路径。 | 把每次决策的输入证据、命中规则、Gate 版本、输出类别及不确定性写入可审计 receipt；对新类型走待分类/通用路径，不能因场景不认识而丢弃。 |

## P0–P2 可执行优先级

### P0：证明“沉淀可用且安全”闭环

1. 按资产类型建立统一 Evidence/Experience envelope：来源事件/主体/时间/版本/scope、Fact 或 Inference、置信/信任级别、证据引用、有效期/撤销状态、关联 ontology 版本。保留原始事实和稳定 ID；重分类只追加。
2. 取真实 Codex 会话建立脱敏、可复现的配对留出集；任务级分组防止同一会话/同源样本泄漏。报告 context 收集的召回/准确、错误前提拒答、更新/冲突、应用成功、误触发、token/延迟/成本和删除/撤销有效性。
3. 每类 candidate 在生成前绑定版本化 Evaluation Contract。合同冻结基线与候选、任务和环境、主收益指标、容忍退化、硬安全断言、评测器版本与样本来源。候选生成者不能改合同。按 ADR-0032 的 shadow→小范围→项目→全局执行；每阶段独立比较，可自动回滚且人可撤销。
4. 对 Capture→Store→Recall→Apply→Feedback→Revoke 做一个可在安装插件后的真实 Host 端执行的服务级验收，不以 mock、单测或设计文档代替实际 hook/MCP receipt。

### P1：提升业务理解和复用质量

1. 把标签演进成可验证的多轴语义引用：业务对象/项目、任务目标/动作、制品/环境、时间状态、验证器、证据类型。Ontology 可以增长和重分类；每个分类变化含本体版本、类别、置信与理由，保留旧快照。
2. 构建“场景之外仍能发现价值”的覆盖集：产品/技术文档、操作系统网页、会议/协作、数据分析、科研、创作及未知任务。场景未知要进入 general/unclassified，而非 ignore。
3. 加入使用反馈的反事实近似：明确记录本轮是否检索/采用了哪一资产版本，结果是否经工具/测试/用户确认；区分资产帮助、无影响、误导。只有“被检索”不能算成功，“使用后成功”也需配对或重复证据避免归因偏差。

### P2：做治理与运维成熟度

1. 为事实和经验提供时间语义（observed_at、valid_from/to、supersedes），项目/全局隔离和过期/撤销传播；不要简单覆盖旧记录。
2. 做自动陈旧检测与重验任务：代码/配置/目录变化、业务状态更新、模型版本变化时，标记受影响经验待验证，而非静默继续复用。
3. 增加 Ontology/adapter 版本兼容检查与迁移预览；低置信/多父类记录进入 unresolved，不参与自动晋级，但保留来源与旧分类。

## 对已定边界逐项核对

| 用户决策 | 研究与方案核对 |
|---|---|
| 全 Craft 可演进 | 支持开放式候选，但“可演进对象范围”不意味着每种对象都能无条件部署；按风险/合同门禁。Core Policy 仍独立。 |
| 自动生成、回归、按门槛启用，人可撤销 | 论文中的自动自改实验不能替代治理；采纳版本档案、真实评测和撤销，但要求不可由候选改动合同/安全门槛。 |
| 场景不成为提取门槛 | 与官方 Skill 触发评测和长期记忆基准相容；用 general/unclassified 处理长尾，场景只做路由和分析切片。 |
| Core Policy 不可自改 | 保留为 Runtime 独立硬边界；ontology labels/adapter/prompt 不得放宽信任、权限、审批、隐私与安全判断。 |
| Facts / Inference 分开 | 将原话、工具观测、外部证据、人工确认、模型推断分字段，并保留来源链；不能用模型自评当独立真值。 |
| 独立配对评测、版本化合同 | 用冻结的匹配任务/环境、基线与候选、独立留出及硬安全门槛；线上数据仅作监控/触发重评，不单独证明因果提升。 |
| 低置信隔离 | `unresolved` 保留原分类和来源，暂不改变召回/晋级行为；已确定样本可以迁移。 |
| 历史可重分类且保留来源/版本 | 仅追加分类版本，保留正文、稳定 ID、旧分类、证据与来源；变更事实正文须走独立候选。 |

## 资料限制

- AnySearch 成功执行了 academic/code 子域发现和论文/代码检索；其结果用于发现来源，不作为最终唯一证据。
- Agent Reach GitHub 的首次查询返回空结果，后续请求触发 `RATE_LIMITED`；依照 Skill 不继续重试。因此不能据此断言相关 GitHub 仓库不存在。改用官方页面和论文原文核对。
- 研究资料的最新日期不等于“业界共识”；部分 2026 论文为 preprint，数字均为其作者在特定实验中的报告。
- 当前代码状态评估限定于已接受文档与已知代码边界。本报告未运行代码或测试，也不宣称本地版本、发布包或真实 Codex 插件已经达到上述验收。
