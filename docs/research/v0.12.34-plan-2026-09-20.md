# v0.12.34 规划：Evidence-Driven Self-Improving Runtime

调研日期：2026-09-20

本文是对当前 Craft `0.12.33` 工作树、现有架构文档和近期一手资料的交叉审查。它只定义下一版的收口目标，不把行业宣传或单次演示当作已验证能力。

## 1. 结论先行

v0.12.34 不应再做“更多能力模块”，而应完成一条可证明的内生学习闭环：

```text
真实 Host
  → Receipt / State Snapshot
  → Deterministic Verification Sensor
  → Failure Attribution
  → Cross-Trajectory Experience Pattern
  → Candidate
  → Shadow / Held-out Eval
  → Signoff / Canary
  → 新 Run 的最小 Context / Activation
```

本版的核心问题不是“Craft 有没有 Memory、Knowledge、Workflow 或多 Agent”，而是：

> Craft 能否从真实可观察结果中判断哪里错了、跨任务归纳出什么、并证明新策略确实比基线更好？

当前代码已经有不少所需零件，但仍存在四类收口问题：

1. `src/application/craft-service.ts` 约 4500 行，兼容门面仍承载过多跨域编排；`service-foundation.ts` 仍有一处向 `interfaces` 的已知向上依赖。
2. `context-retrieval-capture.ts`、`verification-sensor.ts`、`trajectory-abstraction.ts`、`failure-attribution.ts` 等能力已存在，但部分仍以独立 MCP/纯函数存在，尚未由 `VerifiedWorkLoop` 自动串联。
3. `package.json`、`CraftService.VERSION` 仍为 `0.12.33`，源码注释已经出现 `v0.12.34`、`v0.12.36`～`v0.12.41`，版本语义与实现状态发生漂移。
4. `Trace`、`Outcome`、Memory、Knowledge 与 Candidate 的来源关系有数据结构，但还需要一个单一的“验证结论来源”规则，避免调用方自报 `outcome` 再驱动自进化。

## 2. 近期行业事实与对 Craft 的启示

### 2.1 Harness 正在与模型、执行环境分离

OpenAI 在 2026-09-10 发布的 Agents API 将持久会话、长任务编排、子 Agent 和可配置执行环境作为一体化产品，并明确把 Harness 与 Sandbox 分离，以便恢复、扩展和保护凭据。这个方向说明 Craft 的定位正确，但必须把“控制面”和“执行面”做成真正的接口，而不是在应用门面里互相调用。

来源：[OpenAI Agents API](https://openai.com/index/introducing-the-agents-api/)、[OpenAI Agents SDK sandbox/harness](https://openai.com/index/the-next-evolution-of-the-agents-sdk/)

### 2.2 长任务的关键是 durable state、交接和独立验收

Anthropic 的长任务 Harness 采用阶段拆分、结构化交接和独立 evaluator；其结论是，模型自评通常过于宽松，评估器只有在任务确实超出单 Agent 能力边界时才值得付出额外成本。因此 Craft 应保持单 Agent 默认，把 evaluator/sub-agent 作为可评测候选，而不是默认拓扑。

来源：[Anthropic Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)、[Anthropic Agent Evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### 2.3 生产运行时的基础不是“会话”，而是可恢复执行

生产级 Agent Runtime 已把 checkpoint、lease、pause/resume、memory、HITL、tracing 和 time-travel 视为一组基础设施。长历史如果每一步都保存全量快照，会出现 O(N²) 存储增长；delta/checkpoint 与可重建投影比无限追加原始上下文更适合 Craft 的本地事实源。

来源：[LangChain production runtime](https://www.langchain.com/blog/runtime-behind-production-deep-agents)、[Delta Channels](https://www.langchain.com/blog/delta-channels-evolving-agent-runtime)

### 2.4 记忆不是日志，学习也不是把日志搬进 Memory

行业记忆实现逐渐区分 working、semantic、episodic 和 procedural memory，并强调“只让少量经过验证的经验进入长期上下文”。Trace 是证据，Memory 是未来可检索的改变行为的上下文；二者必须保留来源链和回归评测。Craft 的 `MemoryLedger + KnowledgeSource + Context Resolution Receipt` 方向正确，但需要由验证传感器产生写入信号，而不是等待模型主动调用记忆工具。

来源：[LangChain memory loop](https://www.langchain.com/blog/how-to-give-your-agent-memory)、[LangMem SDK](https://www.langchain.com/blog/langmem-sdk-launch)

### 2.5 代码模式和解释器是中间层，不是裸执行入口

程序化工具调用/解释器可以减少工具 schema 和中间结果进入上下文的成本，但它仍然应作为受限 Adapter，不能把模型生成的代码直接变成无限权限。Craft 可以保留 `Trajectory Script Proposal`，本版只完善白名单、验证、可回放和回滚证明，不实现任意脚本执行器。

来源：[LangChain interpreter](https://www.langchain.com/blog/give-your-agents-an-interpreter)

### 2.6 MCP Tasks 是协议互操作，不是安全证明

MCP Tasks 扩展定义 `tasks/get`、`tasks/update`、`tasks/cancel` 和持久 Task Handle。Craft 应继续保留自己的 Policy、Receipt、Trace、Owner/Scope/TTL；MCP Task 只能是外部协议投影，不能替代 Craft 的事实账本。

来源：[MCP Tasks specification](https://tasks.extensions.modelcontextprotocol.io/specification/draft/tasks)

### 2.7 自进化研究正在把“改什么、靠什么反馈、在哪里闭环”分开

近期 Self-Harness、Adaptive Auto-Harness 和 MemoHarness 等研究把自进化拆成 Harness、Memory、Tool/Skill、Routing 等不同轴，并要求反馈信号可以反事实验证。它们支持 Craft 的候选式演进方向，但预印本结果不构成生产准入，也不能替代真实 Case 评测。

来源：[Self-Harness](https://arxiv.org/abs/2606.09498)、[Adaptive Auto-Harness](https://arxiv.org/abs/2606.01770)、[MemoHarness](https://arxiv.org/abs/2607.14159)

## 3. v0.12.34 的模块设计

### 3.1 `VerificationKernel`：把“成功/失败”变成内生事实

新增一个深 Module，而不是继续在 `CraftService` 增加工具方法：

```text
VerificationKernel
  plan(contract, environment, policy)
  observe(receipt, state_snapshot)
  evaluate(checks)
  signals(result)
```

规则：

- 只接受退出码、文件摘要、文件存在性、结构化字段、测试报告等可观察事实；
- `blocked` / `inconclusive` 永远不能当作 `passed`；
- 生成统一 `VerificationResult`，供 Acceptance、Trace Review 和 Experience Capture 消费；
- Host 的“完成”只产生 Receipt，不直接产生成功 Outcome；
- 真实模型/Judge 只能提供诊断意见，不能在未校准时产生晋级事实。

验收：同一输入得到相同 verdict；缺少观察、错误环境、摘要漂移和失败命令均可定位；模型自述不能使失败变成通过。

### 3.2 `FailureAttributionKernel`：先定位层，再允许学习

将失败分为至少以下稳定类别：

```text
coverage / retrieval / grounding / context-budget / scope / temporal
revision / tool-schema / execution / acceptance / synthesis / unknown
```

属性器必须输出：类别、支持它的观察、缺失信号、建议修复层和置信边界。`unknown` 是有效结果，不允许用猜测替代观察。

### 3.3 `ExperienceAbstractionKernel`：跨轨迹而不是单次复盘

当前 `experienceCapture*` 负责单次捕获，`trajectory-abstraction.ts` 已有跨轨迹骨架。v0.12.34 要把二者接起来：

```text
VerificationResult
  → Trace Review
  → Failure Attribution
  → independent Trace/Task recurrence
  → Experience Pattern
```

只有不同 Trace、最好不同 Task，且达到最小重复次数、作用域一致、环境/能力版本可比时，才允许生成 Pattern。Pattern 必须记录：

- 触发条件；
- 失败/成功签名；
- 支持和反例数量；
- 适用作用域与有效期；
- 影响的 Harness 设计轴（最多两个）；
- Evidence 引用和重新考虑条件。

Pattern 不能直接写 Skill、Workflow 或 Prompt。

### 3.4 `ContextRuntime`：把检索、投影和治理约束统一

现有可逆上下文、BM25、混合排序和治理 pin 需要统一为 Context Runtime：

- `Context Resolution Receipt` 记录知识、记忆、经验和约束的版本、选择理由、预算和检索模式；
- BM25/关键词/向量/实体/时间信号都是 Retrieval Adapter；
- 原始上下文不被投影删除，投影可恢复；
- `prohibited_effect`、`required_precondition` 等治理约束不与普通上下文竞争预算；
- 任何 Memory/Knowledge 更新都使相关旧 Context Receipt 失效或待复核；
- 默认不做强制图数据库，关系只作为可选检索和溯源信号。

### 3.5 `AdaptationCoordinator`：唯一演进状态机

将现有候选、评测、Signoff、Canary 与回滚统一为：

```text
Observation
→ Pattern
→ Candidate
→ Shadow
→ Held-out
→ Signoff
→ Canary
→ Route / Rollback
```

候选只允许改变两个设计轴，不能同时改 Model、Prompt、Memory、Tooling、Topology、Verifier 等超过两个维度。被拒绝候选必须保留拒绝原因和重新考虑条件，缺少新证据不得重复生成。

### 3.6 `RuntimeFacade` 与代码分层收口

建议把当前 4500 行 `CraftService` 收敛为兼容门面：

```text
interfaces/                 MCP / CLI / Workbench 适配
application/                Command/Query/Coordinator 用例
domains/control             Task / Goal / Policy / Lifecycle
domains/context             Knowledge / Memory / Retrieval / Projection
domains/execution           Host / Action / Receipt / Recovery
domains/verification        Acceptance / Sensor / Attribution / Eval
domains/evolution           Pattern / Candidate / Signoff / Canary
infrastructure/             SQLite / Content / Trace archive / platform adapters
```

规则：

- MCP handler 不直接读取 SQLite；
- Domain Kernel 不导入 `interfaces`；
- Capability Package 不导入 Application Facade；
- `CraftService` 只负责兼容委派，不新增业务逻辑；
- 移除已知 `service-foundation → interfaces/canonical-tools` 向上依赖；
- 每个深 Module 只暴露少量 Command/Query，复杂校验留在实现内部；
- 版本号不再写进新文件名或逻辑分支，版本信息集中在发布元数据和 Schema Revision。

### 3.7 版本与声明一致性

本版必须一次性同步：

- `package.json`、`CraftService.VERSION`；
- Codex/Claude 主插件和组件插件；
- MCP `serverInfo.version`、CLI `--version`、Workbench health；
- Marketplace manifest、bundle、README 和 release metadata；
- 研究/发布文档的基线版本。

源码中的 `v0.12.36`～`v0.12.41` 注释不能继续代表未发布版本。要么将对应代码归入本版并改成 Schema/设计说明，要么拆成明确的后续规划；不能让注释成为隐式版本路线。

## 4. 真实评测矩阵

本版的验收不是“新增函数覆盖率 100%”而是四层：

| 层 | 目标 | 最小证据 |
|---|---|---|
| 单点机制 | Sensor、Attribution、Abstraction、Context、Governance | 确定性测试和反例测试 |
| Runtime 集成 | WorkLoop 自动产出 Verification/Trace/Outcome | Fixture Host 端到端 |
| 评测可靠性 | baseline/candidate 同环境、等预算、重复配对 | 至少 3 次诊断、5 次才可 eligible |
| 真实 Host | Codex 控制台模式真实执行 | 用户显式配置模型后运行，未配置返回 `unavailable` |

首批 Case 保持两个：研发代码修改、文件型交付。每个 Case 至少测：

- 终态达成率；
- 首次成功率；
- 失败归因覆盖率；
- 无效重试率；
- 中断恢复率；
- Context/Memory 召回准确率和跨 scope 泄漏率；
- Candidate 回归率；
- 成本与时延；
- Trace 完整率。

## 5. 明确不做

- 不默认多 Agent；
- 不做模型权重训练、通用世界模型或 MCTS；
- 不做全局行业树或强制 GraphRAG；
- 不把 MCP Task 当成安全证明；
- 不让模型生成脚本后直接执行；
- 不自动发布或覆盖 Skill/Workflow；
- 不强制向量数据库；
- 不在本版承诺企业多租户、跨设备控制或完整远程 A2A；
- 不建设第二套 Memory/Knowledge/Trace 账本。

## 6. v0.12.34 完成标准

完成后才能说 Craft 接近理想态的本地核心：

> 模型负责理解和提议；Host 负责执行；Craft 负责事实、边界、验证、恢复和受限学习。

具体必须满足：

1. 任意真实 Host 的“完成”都不能绕过再观察和 Verification；
2. 失败经验可以由确定性观察自动进入归因和跨轨迹抽象，但不能直接发布；
3. Memory/Knowledge 只接收带 Scope、Evidence、有效期和撤销关系的候选；
4. 同一 Candidate 的 Shadow/Held-out/Signoff/Canary 状态可恢复、可审计、可精确回滚；
5. 版本、声明、MCP 面、插件包和文档完全一致；
6. 增量代码、函数、分支覆盖率保持 100%，但不把它冒充为真实业务质量证明。

## 7. 长期边界

真实业务 Case 的持续维护、跨平台隔离、企业身份/凭据、远程对象存储和 A2A 多 Agent 仍需真实部署证据。v0.12.34 完成后，下一步应由真实运行数据决定，而不是继续按热点名词堆功能。

## 8. 一手资料补充核验：边界、评测与发布一致性

本节只记录对现有设计有直接影响、且能由一手资料复核的补充结论。

### 8.1 `Agent`、`Harness`、`Context`、`State` 不能互相替代

OpenAI 的 Agents SDK 将 Harness 与 sandbox/compute 分离：Harness 负责模型如何使用文件与工具，sandbox 负责受控执行；状态外置后，运行环境失效仍可从 checkpoint 恢复。Anthropic 的评测定义也把 agent harness 与 evaluation harness 分开，并把最终环境状态定义为 outcome，而不是模型的文字声明。

因此 Craft 的规范关系应固定为：

```text
Agent = Model + Harness
Harness = Context Projection + Capability Activation + Orchestration + Verification/Recovery
Runtime = durable Run/Operation/Lease/Checkpoint/Receipt substrate
State = Control State + Workspace/External State Snapshot
Context = State/Knowledge/Memory/Experience 的受预算投影，不是事实源
```

这意味着 `Context` 不应持有运行真相，`Trace` 不应被当成长期记忆，`Outcome` 必须来自状态观察；任何“模型说完成了”的回执都只能触发再观察。

来源：[OpenAI Agents SDK sandbox/harness](https://openai.com/index/the-next-evolution-of-the-agents-sdk/)、[Anthropic Agent Evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### 8.2 单点能力必须有自己的 Evaluation Contract

Anthropic 明确区分 capability/quality eval 与 regression eval：前者测能力边界，后者保护已通过任务不回退；多轮任务还应分别记录 task、trial、grader、trace 和 outcome，并组合 code-based、model-based、human graders。

Craft 对每个可单独暴露的能力（Memory、Knowledge、Retrieval Adapter、Capability Discovery、Host Adapter、Verification、Experience）应公开同一份最小评测契约：

1. **Mechanism**：确定性单测、schema、不变量和反例；
2. **Conformance**：权限、scope、泄漏、幂等、超时和版本兼容；
3. **Integration**：在 Fixture Host 中验证 Receipt、State Snapshot、Acceptance 的连接；
4. **Quality/Regression**：固定 Case 的能力集与回归集，记录成本、延迟、重试和失败类别；
5. **Routeability**：只有在真实 Host/模型、相同预算和环境指纹下通过配对 Trial，才允许成为默认路由。

“单点测试通过”只能证明机制可用，不能证明该能力值得默认激活；插件/MCP 对 Codex 或 Claude 的可用性还必须有 initialize、tools-list、调用回执和跨版本兼容证据。

来源：[Anthropic Agent Evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### 8.3 Snapshot、Delta 与 Context Receipt 应分层存储

LangChain 对长任务运行时的公开设计指出，全量快照会随步骤数产生 O(N²) 的存储增长，delta/checkpoint 更适合长运行恢复。Craft 因此不应把每次 Context Resolution 的完整正文、模型消息和工作区全量复制到同一账本；应保存不可变摘要、增量差异、版本引用和可重建投影。

建议将以下三类对象明确分开：

- `State Snapshot`：工作区/外部状态的摘要与对象版本；
- `Context Resolution Receipt`：本次给模型的选择结果、预算、理由和版本；
- `Trace Span`：发生过的动作、响应和错误摘要。

它们可以互相引用，但不能合并成一个“上下文大对象”，否则恢复、审计和迁移都会被绑定到模型历史格式。

来源：[LangChain Delta Channels](https://www.langchain.com/blog/delta-channels-evolving-agent-runtime)

### 8.4 可插拔不是“任何模块都能替换”

OpenAI 的 SDK 用 Manifest 抽象统一描述工作区，并通过 sandbox provider seam 兼容不同执行环境；它仍把凭据隔离、快照恢复和执行边界留在 Harness/Runtime 侧，而不是交给任意能力插件。

Craft 应采用“两种可插拔边界”：

- **Capability Adapter**：Memory、Knowledge、Retrieval、Host、Storage 等可替换实现；必须遵守统一契约并带 digest、scope、health、trust 和 version。
- **Core Kernel**：Policy、Receipt、Trace、State Observer、Acceptance、Evaluation、Promotion 不作为普通能力插件替换；它们是所有入口共享的事实与安全边界。

否则单独安装 `craft-memory` 或 `craft-knowledge` 时会产生第二套账本，破坏完整 Craft 与单点 MCP 的结果一致性。

来源：[OpenAI Agents SDK sandbox/harness](https://openai.com/index/the-next-evolution-of-the-agents-sdk/)

### 8.5 版本一致性应同时校验产品版本、Schema 版本和协议版本

当前工作树已经出现产品版本注释与实际发布版本不一致的情况。补充核验后，三类版本必须分别管理：

- **Product release**：Craft、插件、Marketplace、bundle、CLI 的发布版本；
- **Schema revision**：Trace、Receipt、Memory、Knowledge、Candidate 等数据格式版本；
- **Protocol revision**：MCP/Host/A2A 等外部协议版本。

发布检查应验证产品版本在 package、插件 manifest、MCP `serverInfo`、CLI health、Marketplace manifest 和文档基线中完全一致；Schema 与协议版本不能通过修改产品版本“顺带升级”。任何源码注释中的未来版本只能是 roadmap 标记，不能表示已发布能力。

## 9. 对当前设计的直接修正

基于以上核验，v0.12.34 的流程和分层只需做三项原则性修正：

1. **主流程不改成更多步骤**：保持 `Goal/Task Contract → Activate → Preflight → Execute → Observe → Accept → Learn`，把 Verification、Recovery 和 Context Resolution 作为每一步的内核钩子，而不是继续向用户暴露更多流程节点；
2. **单点能力与完整流程共用内核**：单点查询/诊断可以绕过完整 Work Loop，但任何写入、发布、权限变化或外部 Effect 必须回到同一 Policy、Receipt、Trace、Acceptance 和 Eval；
3. **先拆 `CraftService` 再扩功能**：优先把跨域编排下沉到 control/context/execution/verification/evolution 五个 domain coordinator，MCP/CLI 仅做适配，避免用新插件掩盖现有分层债务。

## 10. 目标、计划与普通对话的边界

本轮补充确认主流程中的对象关系：

```text
Goal → Target → Plan → Step → Accept
```

`Goal` 是用户表达的期望；`Target` 是经澄清后的对象、范围和期望终态；`Plan` 是候选执行路径；`Step` 是带前置条件、动作、回执和失败处置的最小单元；`Accept` 是对真实状态和产物的验收。它们分别回答“想要什么、具体要改变什么、准备怎么做、每一步做了什么、是否真的完成”。

普通 `turn` 不需要强制创建持久 Goal/Target/Plan/Run；`goal`、`plan`、`execute`、`verify`、`learn` 是同一 Runtime 上的交互模式投影，不是五套 Agent。只有涉及执行、副作用、验收、跨会话或候选演进时，才进入完整 `VerifiedWorkLoop`。
