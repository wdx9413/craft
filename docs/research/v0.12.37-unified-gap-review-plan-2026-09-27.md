# Craft v0.12.37：当前差距审查与统一收口计划

审查日期：2026-09-27。基线：`9ada1c7a92dfc3847837b063081176696ca9f463` 加当前未提交、未跟踪的实现；保留 `.serena/`，不改用户数据。关联检查覆盖 craft-marketplace、craft-common-use。本文是审查与实施计划，不代表修复、发布或真实平台验收完成。

2026-09-27 研究修订：结合当日打开核验的 Codex、Meta Muse 等一手文档补充第九节。原审查发现不变；执行优先级以第九节的产品里程碑为准。业界能力是参考，不代表 Craft 已实现；厂商公布不等于独立效果验证。Muse 暂按 Meta 的个人 Agent 作为候选，等待用户确认指代。

## 一、结论与理想态边界

Craft 已有较完整的通用控制模型、四个外发子能力、受限执行请求、部分桌面基础及浏览器控制原型。最大差距不是再增加一批概念，而是：**一些回执可以在证据不足时成为成功事实；实现存在不等于真实宿主已经接入；指定测试组通过不等于完整产品收益或平台支持已被证明。**

理想态应是以下可验收状态，而不是无限增加功能：

1. Task / State / Policy / Activation / Receipt / Evidence / Outcome / Eval Gate 保持通用内核；所有能力共享一条授权和验收链。
2. Knowledge、Memory、Experience、Codebase 独立可用；Browser、Computer 只有具备真实 Host、审批和回收链后才作为可用产品发布。
3. Codex / Claude 日常任务能产生可解释、可定位到当前会话的组件使用证据；没有数据时说明原因，而不是泛称“已启用”。
4. Host 终态、动作执行、业务验收、模型收益分别记录；不能互相替代。
5. 桌面和显式启动的无界面 Host 共用控制协议；两个目标操作系统都有真实安装、操作、恢复证据。
6. 对外能力声明、测试范围、发布物与实际证据一致。缺测即未验证，缺配置即 unavailable。

本计划不增加编码专用运行时，不把 Experience 变成自动合并器，不建设图数据库或团队权限的空壳；保持当前分支及版本。后续实施不应顺带提交、推送或迁移真实用户数据。

## 四、主审补充：已复现的信任链问题

### M1 / P0：Host 终态不是严格解析的事实

`core/codex-driver.ts:27`、`:67` 将退出码为 0、未超时、JSON 行可解析视为 completed，没有强制正确终态及取消状态。

在临时 Store 中对实际 CodexHostKernel 注入确定性执行输出，分别得到：

```text
empty JSONL                    → receipt_status=completed
turn.failed                    → receipt_status=completed
cancelled + turn.completed     → receipt_status=completed
```

这些是解析器复现，不是调用真实模型。修复需要明确 JSONL 生命周期状态机：缺终态、failed/error、截断、取消、超时、非法顺序、矛盾终态均不得 completed。自然语言最终回答不能补足终态或验收。

### M2 / P0：Automation 可接受另一任务或重复使用的观察

`capability/craft-experience/procedure-automation.ts:139–164` 主要检查 Host session、trace 和 observer 身份不同；没有完整绑定当前 Task、Activation、dispatch、Procedure 版本、验收定义与 Evidence 可信状态。

使用既有 fixture 和实际服务在临时 Store 中复现：另一任务的 Host session、相同 passed Observation、unverified Evidence，被两个不同运行分别接受为 accepted。当前 `progress.changed` 还被固定为 true，新增 receipt 本身不能证明任务进展。

修复：导入必须验证上述完整绑定、终态及独立验收；结果不可跨运行重放。进展由相关世界状态或任务里程碑决定。失败、无进展及配额耗尽只产生 handoff，保持 awaiting_host_dispatch 边界。

### M3 / P1：Knowledge 在审阅包不可用时也能晋升 reviewed

`core/knowledge-auto-review.ts:173–251` 的 packet_digest 可选；MCP 工具目录亦未要求它。host_run_key/model_ref 是输入字符串，并不自动构成 Host 身份证明。

临时 Store 复现结果：`packet_status=unavailable, promoted=true, packet_attested=false`。既有 promotion-policy 测试中还有覆盖此宽松路径的成功断言。

修复：新的 supported 晋升必须绑定不可变审阅包、Claim 版本、Source Revision、Fragment、Evidence 和真实审核来源；旧兼容输入保留但标为 revalidation_required。包摘要证明“审了什么”，本身不证明判断正确，更不等于独立审核。

### M4 / P1：受保护评测工作流尚未自包含

`.github/workflows/engineering-eval.yml` 准备 Node/pnpm 和构建，但没有声明 Codex CLI 安装、版本固定与准备检查；`scripts/engineering-eval.ts:27` 随即调用 codex。不能依赖 clean runner 偶然预装它。

另外，临时 Case 副本无 Git 元数据，当前执行参数没有 `--skip-git-repo-check`；本机 CLI 帮助确认该选项用于允许仓库外执行。应做真实单 Case 冒烟决定受控例外或临时仓库初始化方案。本文没有运行远端工作流，故不将此说成已经取得的远端失败日志。

### M5 / P1：common-use 安装事务不是全目标事务

`../craft-common-use/init.mjs:385–443` 有预检与部分 MCP 回滚，但 Skill 写入/卸载和多个目标不处于同一完整恢复事务。后续 I/O 失败或预检后的竞争仍可能留下半安装状态。

修复：全部目标所有权检查、MCP/Skill 快照、暂存和原子替换、完整回滚日志覆盖安装与卸载；注入每个失败点验证旧状态完整恢复。不删除不属于 Craft 的配置或 Skill。

### M6 / P1：同版本不代表当前安装物或当前会话

`core/activation-proof.ts:45–65` 在没有 session_id 时可聚合历史收据，以 release 版本过滤并不能识别同为 0.12.37 的不同构建。

doctor 应绑定 session、project、data space、Host 和 artifact digest，明确“当前版本”“当前挂载”“Hook 执行”“Context 使用”“写入并验证”五种不同证据。不能用一次 readiness 调用补造业务使用记录。

## 五、能力差距总表

| 领域 | 已有基础 | 距理想态还缺什么 |
| --- | --- | --- |
| 通用运行内核 | Task/Policy/Receipt/Acceptance、配额与 handoff | 将所有真实执行入口接入同一验证链；处理重启、并发、重复回执与 effect_unknown |
| Knowledge | 来源修订、片段、候选 Claim、过期状态、历史修复机制 | 可信审核包；原子 Claim 提炼；实体/关系去重；fragment 级增量复用；高频 stale 告警及来源复核 |
| Memory | scope、topic、时间、supersede/revoke、事件保留 | subject/predicate 事实槽位及策略类：住址替代、戒糖期限、deadline 到期、依赖来源漂移分别处理 |
| Experience | Observation/Pattern/Procedure、候选和晋级、受限派发 | 修复验收绑定；真实进展；独立验证的日常样本；证明错误复发减少而非记录数量增加 |
| Context | Resolution、决策门禁、约束与缓存指标结构 | 强制关键决策重解析；从 Host/验收取得指标，不接受调用方自报即当事实；证明少输入不降能力 |

| Browser | 受管 Chromium、CDP、ControlSession、隔离本地 smoke | 产品 Host、审批 UI、表单状态绑定、恢复、导航边界；iframe/Shadow DOM/截图等须逐项声明支持 |

| 团队/长任务 | Bundle、冲突候选、受控运行模型 | 真正身份/ACL/签名撤销、调度宿主/恢复/通知是后续独立项目，不由 scope 枚举或循环函数代替 |

Codebase 继续放在可选能力层；语义分析的 Provider/Adapter 与 Craft 的 checkpoint、Policy、Evidence 契约分离。Serena 可以共存或作为显式外部 Provider，不宣称当前已集成。不要为了替代所有工具而重造完整 LSP/图数据库。

## 六、统一执行计划

以下是工作包，不改变前面两个独立审查轴的等级。允许没有共享写入冲突的工作并行，但发布门禁必须按依赖通过。

### G0：先修成功事实与授权绑定（P0，第一批）

- 覆盖 M1、M2、M3、S1：先将上述复现固化为失败回归，再修终态、验收绑定、审核包及动作状态。
- 复用现有 HostSession、Evidence、Acceptance 和恢复模型；不引入另一套“可信系统”。
- 所有边界含取消、截断、重复、并发、漂移、缺证据测试。既有测试若认可错误语义，应修断言，不以删除有效测试达标。
- 同步检查通用交付评测：`core/delivery-evaluation.ts` 当前将 `ready_for_delivery` 与 `accepted` 都计为 quality=1。不得把“待交付、尚无独立验收”作为业务成功；比较所需模型/环境/预算应绑定原始 receipt，而不只是接收比较参数。此项为本次追加源码发现，尚未新增运行复现。
- 验收：四项复现均被拒绝或 handoff；正常路径有完整匹配证据；旧记录不被自动升级可信度。

### G1：覆盖率与能力声明基线（P0，与 G0 配套）

- 自动生成新增/修改生产逻辑清单；每个文件映射到覆盖报告，不能仅验证手工选定的组。
- Node 行/函数/分支均 100%；浏览器实际执行脚本及原生 Rust/helper 单独提供有效报告。排除项只允许无执行逻辑并附理由。
- 更新 README、当前能力矩阵、Codebase 发布说明、Experience 自动化和 Context 文档。历史研究保留日期与后继文档链接，不改写历史。
- 验收：新增生产文件遗漏即门禁失败；测试通过率与覆盖率分开报告；未完成平台仍为未验证。

### G2：真实评测 runner 可复验（P0，晋级依赖 G0）

- 修 P1、M4：固定 CLI/模型/环境/预算，规范 Host JSONL/usage；不存在的信息不得补 0。
- 定义重试事件、输入/输出/缓存 token 和成本口径，价格版本可追溯；无法取得成本时不得得出“成本未恶化”。
- 完善单 Case 诊断入口、临时工作区准备、超时/取消/失败 archive 和 finally 清理；验收器、双 sibling 及根因引用分别留证据。
- 验收：先真实单 Case baseline/profile 冒烟；再完整 12 Case × 5 配对。缺配对、blocker、指标不可比或恶化均不晋级。
- CLI JSONL 继续用于批量试验；另验证公开 Codex App Server 作为交互 Host Adapter 的适用性，承接流式事件、审批、取消与恢复，不能据此声称获得 Codex Desktop 私有浏览器/应用控制能力。
- 普通 CI 不调用模型、不用密钥；受保护 workflow_dispatch 单独运行。报告索引允许引用外部 artifact，不将敏感正文入库。

### G3：让日常使用与历史数据可见（P0/P1，可与 G2 并行）

- 修 M6：doctor 输出当前 session、实际插件 artifact digest、MCP 挂载、Hook 执行、Context Receipt、各组件可读数据及未使用原因。
- 分别完成 Codex/Claude 的来源事实查询与审核、显式“记住”、修改后验证三个真实流程；失败分类到权限/来源/Hook/数据空间等具体原因。
- 历史 Knowledge/Experience 先 dry-run 统计，再通过明确授权执行可恢复迁移；缺来源或新 receipt 绑定的保留并标为 revalidation_required。
- 验收：每个 canary 有 Task/会话对应的 receipt 与可读结果，撤销/回滚可验；不以历史“106 条”当当前实测数量。

### G4：完成一个受控浏览器产品闭环（P1，依赖 G0）

- 建立 Desktop 和显式 CLI 共用的本地 Control Host：loopback、受限凭据、项目绑定、角色分离、到期及并发控制。
- 提供审批/接管 UI；模型调用面无法伪造批准。完成 session_open→observe→prepare→approve→execute→independent observe→close。
- 统一旧 CDP/Edge 路径；修 S2/S3/P4。启动失败、超时、进程退出、重启中断能清理或 reconcile。
- 站点限制区分主动阻止与事后检测；在没有请求/导航强制约束时，不宣传网络级隔离。
- 验收：受控本地表单上，桌面/无界面均有真实审批、状态漂移拒绝、effect_unknown 恢复和接管证据。

### G5：原生应用、Webview 与六插件交付（P1，依赖 G4）

- 固定动作 Webview 桥；页面不能取得通用 Tauri 权限或任意 JS 执行入口。
- macOS/Windows helper 由系统 SDK 在构建阶段准备；权限、应用/窗口、DPI、截图摘要与坐标绑定，结构化控件优先。
- 高风险动作逐次批准；密码/验证码/安全提示交用户。截图最小范围、短生命周期，成功/失败/重启均清理。
- 两平台分别真实安装、启动、观察、批准、操作、验收、接管；无机器/权限时记录未验证，不用 mock 代替。
- 通过后才增加 craft-browser、craft-computer 的薄 MCP/Skill 外发包装；从同一 distribution contract 同步三仓，隔离安装验证不可切换 full。

### G6：分层与发布事务收口（P1，贯穿上述实现）

- CraftService 保持兼容门面，但完整用例移交 Cognitive、Runtime、Capability、Quality coordinator；foundation 只装配。
- Capability 拥有领域规则，Adapter 只实施外部操作，接口层负责协议与呈现。不要以 core/domains 再导出目录伪装已完成领域拆分。
- Workbench 按页面、状态生命周期、API 客户端拆分；不新增重叠状态源。Desktop 只拥有窗口/权限/Host 生命周期。
- 保持真实导出来源、动态导入、barrel 和循环依赖审计；增加完整用例跨层测试。
- 修 M5：全安装/卸载事务和故障注入。来源 digest 与 artifact 自校验之外，补齐构建输入、锁文件、工具链到实际 artifact 的可核验关联。
- 验收：隔离包无源码启动、用户配置不丢失、半安装可回滚、三仓产品面一致。

### G7：子能力质量提升（P1，可信基础完成后分组件推进）

1. Knowledge：先做 README/AGENTS/Markdown 的原子 Claim 与 fragment 增量保鲜，保留精确来源片段；再做去重、过期复核与热点告警。
2. Memory：引入有界事实槽位策略，分别测试当前/历史住址、戒糖期限、deadline 失效、依赖版本漂移；压缩只创建派生摘要。
3. Experience：使用真实独立结果积累候选流程，评测错误复发与终态；流程只在明确授权下 materialize/dispatch。
4. Context：稳定前缀、Task/State、决策材料、按需引用分层；关键决策点强制最小重解析。缓存由 Host 事实报告，否则 unavailable。
5. Codebase：先建立 import/caller/重名/动态调用/版本漂移的 gold cases，再选择现有解析能力或显式 Serena 等 Provider。运行依赖与打包成本需单独核验，不默认把 devDependency 变运行依赖。

验收：每项既有确定性正确性报告，也有独立组件 baseline/candidate 对照；不将整体 prompt 改动的收益归因给单组件。

### G8：最终收益与发布门禁（依赖前述相关工作包）

- 工程修复和文件型交付两类真实任务；Knowledge/Memory/Experience 分组件控制变量，固定模型、Host、项目快照、预算和验收器。
- 诊断可 3 配对；正式比较采用 5 配对并说明样本限制。Engineering Profile 仍按完整 12×5 契约，不能用另一评测代替。
- 指标分别覆盖事实/来源正确性、偏好命中/跨项目泄漏、错误复发/终态/无效重试、约束召回/误注入、token/缓存/成本/时延。
- 无真实数据不得称持续进化或收益已证明；测试、真实 Host、平台安装、收益报告、发布 artifact 五类证据分开归档。

推荐先后：**G0 → G1/G2/G3 → G4 → G5 → G8**；G6 随每个改动推进，G7 按组件独立验收，不阻塞先修可信性。

### 后续独立项目，不混入本轮

- OS 调度/守护进程、真实 Sandbox/Credential Broker、通知与跨崩溃恢复演练。
- device/principal 身份、团队 ACL、签名 Bundle、撤销授权与传播。
- Tracker/worktree/Draft PR/CI verifier/merge Adapter：每一项单独授权、评测和隔离，不加入 Experience 内部。

## 九、结合业界后的产品计划修订

### 9.1 定位：通用任务交付，而不是另一个编码壳或插件集合

建议将产品目标明确为：**Craft 是可跨 Host 使用的通用任务工作台，让用户把目标、材料和边界交给 Agent，得到可检查的成果；同时让权限、记忆和执行过程可见、可撤销、可恢复。**

这是产品判断，不是市场份额或用户调研结论。本文的用户诉求假设来自一手产品能力及既有 Craft 需求，实施前应通过目标用户任务试用验证，不以“热点”代替需求证据。

- 在 Codex/Claude 中：提供独立插件及可信上下文/证据契约，尊重宿主已有交互和工具。
- 在 Craft Desktop/Workbench 中：面向不写代码的用户提供任务、成果、待确认事项、连接和记忆管理；不要默认展示内部对象图。
- 在显式无界面 Host 中：提供同样受限的任务执行与恢复，不偷偷安装 daemon。
- 这三种入口共用领域规则，不能演变成三个重复运行时。

### 9.4 新增或前移的工作项及架构落点

**A. 成果与人工接管工作台（前移，P1）**

- 复用 `core/work-delivery.ts` 的 Host/Acceptance 分离与既有 Delivery/Evidence，增加交付文件版本/digest、预览、差异、来源和重做入口；预览状态不写 accepted。
- 默认界面是任务、成果、待确认、连接/记忆四类视图。内部 Receipt ID 留在可展开详情，不要求用户掌握内部术语。
- 路径落在 application 用例与 Workbench 接口层；格式处理由可选 Capability/Adapter 提供，Desktop 只打开视图。
- 验收含路径逃逸/符号链接、外链和可执行 HTML 预览隔离、敏感内容脱敏；未经批准不分享/发布。

**B. 公开 Host 适配与能力探测（前移，P1）**

- 首先复用 `core/host-driver.ts` 与 HostSession，CLI 保留批量 runner，App Server 作为交互适配实验；完成真实 stop/resume/approve/terminal/usage 契约测试后再产品化。
- 能力表区分文档支持、当前探测、实际调用证据。多宿主不要靠统一名称假设等价，也不以具体模型版本写死领域规则。
- 网络、上传、GUI foreground 占用、截图传给哪个 Host 等成本/权限信息在执行前展示。

**C. 权限权威、凭据与数据出站（前移为前置门禁）**

- Core 保持声明式 Policy/Grant/Receipt；application 组织用例；受信任本地 Host/平台 Adapter 持有实际权限、秘密与执行句柄。
- 模型仅提出结构化动作；批准由受信任控制面签发并绑定 principal、Task、目标、参数摘要、期限和次数。撤销必须作用于待执行动作，不只修改页面状态。
- 浏览器页面、文件、连接器响应和候选 Skill 一律作为不可信输入；禁止它们改变策略或要求发送秘密。图片/截图内容同样纳入注入测试。
- 外部写入前实现最小凭据隔离、目标/方法/载荷约束与出站检查；没有真实 OS/网络约束时明确不具备沙箱级隔离。此项不是当前轮立刻允许真实发送或付款。
- `core/capability-connector.ts` 目前主要登记元数据、健康与 ticket，不等于已有带认证的传输。注册中的 approved/approval_ref 不能直接成为未来执行授权。

**D. 持续任务最小闭环（从“全部远期”调整为分阶段）**

- 近期只做一个显式启动、预算受限、只读来源的持续任务，不新增后台守护服务。借助已支持的 Host 调度或人工调用 tick，并记录来源事件、去重键、lease、游标和 handoff。
- Workbench 提供“什么时候再检查、为什么暂停、下一步需谁处理”，静默无变化；通知投递为 Adapter，用户可静音/撤销。
- 独立 daemon、云端 24/7、手机远程控制仍为后续范围。现有 MaintenanceScheduler 是认知维护调度，不应直接改成通用任务执行器。

**E. 示教与交互式插件（后续，P2）**

- 示范输入需明确同意、限定窗口/时段、可停止、去敏与删除；先导入已经授权的轨迹，暂不建设全局活动记录。
- 录制交给 Adapter；Experience 只接收有来源的候选步骤和待验证假设。Skill/Procedure 正文依然按 Task/Policy materialize。
- MCP Apps 用于宿主内成果/审批视图；WebMCP 用于网站动作发现，两者分别探测与适配。普通 MCP 文本/结构化结果始终可用。

### 9.6 产品收益与未来方向的证据标准

- 在已有正确性/成本指标外，增加首次成功耗时、用户返工轮数、人工看护分钟数、每次有效交付成本、非必要打扰次数、恢复成功率。必须定义采集方法，缺数据不补零。
- 5 次配对适合发现回归和初步比较，不足以宣称广泛统计显著或所有工作负载收益。单一目标宿主与多个宿主分别报告；保留未完成/取消/失败样本。
- 安全测试包含恶意页面/文档/图片、伪造审批、凭据外传、错误收件人、事件重放和跨项目串读。模型审查只能辅助，不取代执行边界。
- 未来判断：结构化连接与 GUI 会并存；文件/成果交互会比单纯聊天更重要；长期目标和个性化需要可靠状态与权限。以上是基于现有方向的推断，不是已发生的普遍市场事实。
- 暂不投入：自研基础模型、全量办公套件、图数据库优先、默认多 Agent 群体、自动交易、全局监听式记忆、无可信凭据隔离的云管家。先验证用户是否减少工作量。

详细业界候选、来源与不确定性见[配套一手资料研究笔记](general-agent-industry-primary-sources-2026-09-27.md)。Muse 的最终指代仍待用户确认，不影响上述基于多个独立产品来源的架构结论。
