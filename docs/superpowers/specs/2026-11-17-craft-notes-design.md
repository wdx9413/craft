# Craft Notes 设计稿

状态：待用户批准；本文件是设计，不代表已经实现。

## 1. 目标

Craft Notes 为设备、目录和单文件保存简短、稳定、对后续任务有帮助的说明：

- **Device Note**：每台已登记设备必须有说明，由用户填写或确认。
- **Directory Note**：仅为重要目录形成备注候选，不把每次路径访问都变成长期注记。
- **File Note**：仅为重要文件形成备注候选；默认不读取文件正文来推断说明。

目录和文件的频繁使用只是重要性的证据之一。系统先生成候选，用户确认后才进入正常检索。来源不明的推断不能变成事实。备注是上下文提示，不是权限或审批规则。

## 2. 当前基线

- `craft-capability/capability/craft-file-dir-desc/file-dir-desc.ts` 当前主要实现目录备注，以 `(device_id, path)` 区分目录，并按原始 `use_count` 达到 3 次晋级。
- Craft 的工具目录和测试已调用设备注册、启用、停用等接口；当前子能力 TypeScript 源码和其 `dist` 没有这些方法。Marketplace 已打包的 Context bundle 却含有独立 `device` 记录与管理方法，且设备数据没有说明字段。这些实现需要先统一，不能在分歧版本上继续叠功能。
- 当前没有单文件备注模型。现有目录记录使用 `file_dir_desc` 存储种类与 `craft_file_dir_desc_*` 工具名。
- Workbench 和 Craft Context 已有显示与工具接缝；不新增一个未限定权限的完整 MCP 工具面。

以上是本地工作区静态检查，不表示 Marketplace 包已更新或实际 Host 已验证。

## 3. 方案比较

| 方案 | 取舍 |
|---|---|
| 每种对象各建一套 Notes 能力 | 语义隔离直观，但证据、确认、撤销、检索和 UI 会重复实现。 |
| 一套强类型 Notes 记录，按对象配置生命周期 | 共享来源、版本和撤销机制；设备、目录、文件仍可采用不同的必填规则和晋级门槛。采用此方案。 |
| 把所有内容作为自由文本 Knowledge | 可以复用检索，但无法稳定绑定设备/路径，也很难对生命周期和风险提醒做一致约束。不采用。 |

**决定：**采用第二种。用户可见名称为 Craft Notes / `craft-notes`。为兼容现有调用和数据，第一阶段保留 `@craft/capability-file-dir-desc`、`file_dir_desc` 和 `craft_file_dir_desc_*` 作为内部兼容标识；新接口可以使用 Notes 名称。是否另发独立 Host 插件不在本次范围内，Notes 继续随 Craft Context 提供有界工具。

## 4. 记录与身份

每条 Notes 记录至少包含：稳定 ID、对象类型、对象身份、短说明、生命周期状态、来源/依据引用、创建和更新主体、时间、版本、复核状态及撤销信息。保存使用的任务/会话 ID 和内容无关证据引用；不保存提示词或文件正文作为来源证明。写入说明前调用现有 DataSec 凭证检测；密钥、口令、Token 和含凭证的 URL 拒绝保存，普通文字“使用本地模型/代理”不因关键词单独拒绝。

- Device 的身份是稳定 `device_id`。设备说明作为 `subject_type=device` 的必填 Notes 记录与设备元数据分开保存；设备启用要求存在已确认说明。不由健康状态、地理位置或网络代理信息自动生成。
- Directory 的身份继续是 `(device_id, normalized_absolute_path)`。跨设备解析只有在显式匹配已验证的仓库身份时才允许；备注不会合并物理目录记录。
- File 的身份是 `(device_id, normalized_absolute_path)`。候选或确认时若调用方已合法获得路径，可读取文件大小和修改时间作为本机元数据指纹；不读文件字节或正文。指纹变化只表示需要复核，不证明文件内容或安全属性。无法取得元数据的远端文件标记为 `path_only`，展示复核时间，不声称能检测内容变更。
- 敏感性和作用范围沿用 Craft 的本地/项目存储隔离。不能因为记录里出现 `production`、`secret` 或 `read-only` 字样，就授予或撤销实际访问权。
- Context 只在任务与 Note 的设备、项目、目录或文件身份匹配时返回已确认 Note；不做全局注入。返回前使用现有 DataSec 和数据外发策略；外发判定不可用时，不自动注入模型上下文，但保留显式本地读取。Notes 不建立绕过数据治理的新通道。

## 5. 重要性与生命周期

### Device Note

新建或启用一台设备时要求 1–500 字符的说明。编辑说明必须作为显式用户行为。已有无说明的设备进入 `needs_note`：保留其现有状态、只读目录解析和健康上报；在补齐说明前阻止重新启用及新增目录/文件 Note。Workbench 提示补齐；不得用设备名、路径或模型猜测来冒充用户描述。无交互的 MCP/CLI 新建或启用请求若缺少说明，返回稳定的 `DEVICE_NOTE_REQUIRED` 错误。

### Directory Note

只有以下任一条件满足时才创建备注候选：

1. 用户显式要求记下/固定该目录；或
2. 30 天内至少 3 个不同任务、横跨至少 2 个 Host 会话，且任务结果有可核验的使用证据。

使用依据限于已完成且有结果记录的 Task/Procedure 中明确绑定的项目目录，以及显式的用户固定操作。只保存任务 ID、Host 会话 ID、时间和结果引用，不保存提示词或文件/目录内容。同一任务中的重试、重复 Hook、扫描器访问和失败派发不计为独立使用。常见临时目录、缓存、生成物和依赖目录默认不触发候选。达到门槛只生成待确认候选，不自动进入正式检索。

### File Note

只有用户显式标记重要，或 30 天内至少 3 个不同任务、横跨至少 2 个 Host 会话且该文件与已确认成果/Procedure 有证据关联时，才生成候选。第一版仅接受现有 Task/Procedure 产物中明确记录的文件路径和 Codebase 中绑定到文件的已确认使用引用；没有这些无内容信号时，只能通过用户显式固定生成候选，不新增对 Host 文件打开行为的普遍监听。普通打开、索引扫描、搜索结果曝光和自动格式化不算有效引用。候选不读取文件正文；系统可以基于路径、仓库身份和已验证的任务引用给出空白模板或明显标记为“建议”的短草稿，用户必须确认或改写后才能生效。

### 通用状态

生命周期为 `candidate → confirmed → needs_review / revoked`。候选不参与默认检索；确认后才参与检索。确认记录绑定精确对象身份和候选版本；重新编辑产生新版本，保留旧版本。撤销立即停止正常检索但保留审计。系统不能用后续观察覆盖用户写下的内容。

`safety_sensitive` 是提醒等级，不是自动写入捷径。涉及生产、凭证、只读或破坏性风险的备注只能由用户明确确认；显示时标注其时间与依据，权限系统仍须独立拦截危险操作。

## 6. 旧数据迁移与兼容

- 现有 `file_dir_desc` 目录记录迁入统一 Notes 投影时保留 ID、正文、设备、路径、仓库身份、计数、状态、时间、撤销信息和来源；不改写正文、不推断 File Note。
- 旧 `promoted` 记录标为 `legacy_unreviewed`，继续保持原有可召回行为并返回旧来源标记；Workbench 提供复核入口。用户确认后转为正式 `confirmed`；明确撤销则停止召回。此兼容仅限迁移前已晋级的记录，新候选必须经人工确认。
- 旧 `observed` 保持不参与默认检索。旧撤销记录继续不可召回。
- 已登记设备没有 Note 时标为 `needs_note`，不补造说明。迁移不得扫描文件或读取正文。
- 旧 MCP 工具和存储键提供兼容映射；一段迁移期后再根据实际使用情况决定是否弃用，弃用前不删除接口或数据。

## 7. 边界与非目标

- 本能力只保存和检索备注，不自动修改文件、设备配置或审批策略。
- File Note 中的“只读”“勿改”等文本本身不构成安全控制。
- 默认不读取文件正文；路径和已确认备注经过现有数据外发策略，提示词与文件正文不作为 Note 来源上传。
- 不把每个设备属性、每次打开记录或所有文件访问永久保存为 Note。
- 不在此阶段创建独立 `craft-notes` Host 插件；Host 侧仍使用 Craft Context 的受限工具和 Workbench 展示。

## 8. 跨仓实施与验收

1. **craft-capability**：统一设备、目录和文件的类型模型、身份校验、候选门槛、确认/撤销生命周期及旧记录兼容；包源码、构建产物和既有类型定义保持一致。
2. **craft-common**：只在当前存储接口不能表达统一记录/迁移所需的事务或作用域时扩展；不得为 Notes 引入平行数据库。
3. **craft**：提供兼容旧工具的新 Notes 操作；真实任务使用信号去重并保留任务/会话依据；普通设备注册缺少说明时失败关闭；检索只返回已确认、有效且身份匹配的备注。
4. **craft-workbench**：设备首次登记必须填写说明；目录/文件候选进入清晰的确认队列；展示候选理由、时间、依据、版本和风险提醒；允许改写、确认、撤销。
5. **craft-marketplace / craft-eval**：从同一个已版本化来源生成包；Eval 覆盖三种对象的候选、确认、迁移、复核和安全误用边界。发布包必须标记真实来源提交和构建版本。

验收至少包括：设备缺少说明时无法新建/启用；说明只由用户输入或确认；同一任务重复调用不累计独立频次；目录与文件按各自门槛产生候选；未确认候选不可检索；确认后限定在正确设备/项目；文件身份变更触发复核；危险备注不绕过审批；撤销立即停止召回且留存审计；旧目录记录迁移前后稳定 ID 与历史行为；旧接口保持兼容；源码、构建产物及 Marketplace 包提供相同能力。

增量代码需按仓库要求达到 100% 行、分支覆盖。Host 真实交互、不同设备间的授权和新 Marketplace 安装作为独立验收，不能由单测替代。

## 9. 待实现的默认选择

- 30 天滚动窗口、目录 3 个不同任务/2 个会话、文件 3 个不同任务/2 个会话作为第一版固定阈值。
- 重要性信号生成候选，不自动确认或自动发布。
- 设备说明由用户在创建时填写；旧设备提示补充，迁移不猜测。
- 文件变化仅使用可得的大小/修改时间作复核提示，不读取正文；无法取得元数据时保留 `path_only` 状态。
- 不新增普遍文件访问监听；频率候选只使用 Task、Procedure 与 Codebase 已绑定的内容无关证据，信号不足时退化为用户显式固定。
- Notes 首发随 Craft Context 提供，不创建独立 Host 插件。
