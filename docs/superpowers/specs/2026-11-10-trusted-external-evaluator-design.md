# Experience 可信外部评测器设计

状态：设计草案；外部签名回执尚未实现。

## 1. 结论与范围

由部署管理员在评测调用接口之外配置治理根公钥，并签署可信评测器的 Ed25519 公钥和授权范围。Craft 签发绑定候选版本、阶段、评测合同和一次性随机数的请求；外部评测器签署包含请求摘要和逐案例结果的回执。Craft 验证签名、授权、合同和时效，在主库的同一发布事务中消费请求、发布证据指针和推进门禁。没有可信配置时保持失败关闭。

此设计覆盖 Graph、Prompt 和外部 Workflow 适配器的四阶段晋级。它不把任意 Workbench 评测、自报 `confirmed`、自签名公钥、租约持有者或模拟运行变成可信评测；也不证明可信评测器没有作恶。独立真实 Host、模型真实性和用户收益仍需要各自的证据。

## 2. 已核实的基础

- `capability/craft-experience/learning-evaluation.ts` 已按候选版本、定义摘要、阶段和基线版本建立调度；正向门禁要求内部评测器来源的证据。当前自动执行器仅支持只读 Workflow。
- `core/application/use-cases/durable-experience.ts` 的内部评测器保存带来源标记的证据；调用方直接声明来源不能作为信任依据。
- `core/hub-sync.ts` 使用 Node 加密库验证 Ed25519 签名，`core/supply-chain-attestation.ts` 使用公钥和指纹管理证明。它们的注册接口不构成外部评测授权，不能直接作为本方案的信任根。
- Eval 报告中的运行身份是调用数据的摘要，其 `evidence_origin` 为 `unverified`。摘要可用于一致性检查，不能证明执行位置或模型身份。

以上为当前工作区代码事实，不代表远端已部署或真实 Host 已通过验收。

## 3. 方案比较

| 方案 | 优点 | 限制与选择 |
| --- | --- | --- |
| 仅依赖租约、调用方身份和报告摘要 | 接口简单，易于重试 | 调用方可自行构造通过结果，无法抵御伪造，不采用 |
| 仅允许 Craft 内置执行器 | 信任边界最小 | 不能支持 Graph、Prompt 和外部运行环境，继续作为默认回退 |
| 管理员配置公钥、评测器对精确请求签名 | 可跨进程和跨主机验证，私钥不进入 Craft | 需要独立密钥管理和评测器治理；本设计采用 |

签名认证的是密钥持有者及其声明。它不证明配置的评测器独立、执行真实，或测试集没有泄漏；这些性质由配置治理、执行凭证和独立验收分别验证。

## 4. 信任根与威胁模型

治理根公钥由部署管理员通过受保护的运行时启动配置注入；普通 MCP、Workbench、项目文件和评测报告均不得创建、替换或启用它。治理根签署单调递增版本的评测器授权和撤销记录，验证后写入 Craft 主库；主库是各进程消费时唯一的活动策略权威，不以进程缓存或文件修改时间判断撤销。策略至少包含 `policy_id`、不可变版本、Ed25519 公钥指纹、评测器及治理主体 ID、项目范围、允许的 Procedure 类型及阶段、生效时间与撤销状态。导入治理记录与消费回执争用同一主库写锁，以先提交者为准；消费时在锁内重新读取当前策略。配置来源必须由部署方限制写入；若 Craft 和不可信评测代码共享同一操作系统身份且都能写该配置或数据库，则该隔离假设不成立，禁止宣称防伪。

签名私钥仅由独立评测器持有，治理根私钥仅由管理员持有。日志、数据库和工作区不保存私钥；不接受请求携带公钥作为信任依据。密钥轮换添加新策略版本并停用旧版本，历史回执保留用于审计，未消费回执在策略撤销提交后不能晋级。数据库恢复到旧快照可能回退撤销记录：部署方必须提供受保护的外部最新治理版本检查点；缺失、不可用或检测到回退时禁用外部晋级，直到重新同步并核验。系统时间不可用或明显不可信时拒绝有时效的回执。

策略必须按阶段配置可审计的治理主体及职责：Held-out 用例由独立于候选开发和选择的主体冻结并授权，Signoff 必须由与候选开发者和执行评测器不同的授权主体签署；禁止单个密钥或主体包揽四阶段。主体关系来自管理员签署的策略，不采信回执自报。无法证明隔离时保持失败关闭；签名无法保证这些主体之间不存在现实中的合谋。

时间校验使用部署方配置的独立可信时间服务，Craft 在认证通道上实时发出一次性随机挑战，服务签署挑战和当前时间；以本进程单调时钟限制从发出挑战到消费提交的总耗时，超限或跨进程重启即丢弃证明。消费时在主库记录时间下界。证明签名错误、时间低于下界或服务不可用时拒绝晋级。重启或恢复旧快照后先取得新证明并核对受保护的外部检查点，检查点响应也须绑定新挑战并限制往返时间，不能仅依赖本机时钟。实际部署如何提供这些服务属于交付前置条件，当前尚无此能力。

## 5. 请求与回执

服务端创建请求，绑定：协议版本、随机请求 ID、调度 ID、候选 ID 和精确版本、定义摘要、阶段、基线 ID 和版本、项目范围、场景评测合同摘要、阶段用例集及每个用例摘要、评测器及策略版本、环境、预算、Host、模型和工具配置摘要、签发和截止时间。摘要均由服务端从已固定的合同计算，禁止用回执自报值替代。Held-out 用例与训练输入的隔离由受控用例目录和评测策略提供，布尔声明本身不足以证明独立性。

评测器签名的规范化信封包括上述请求摘要、唯一回执 ID、开始和结束时间、每个预期案例恰好一次的输入摘要、结果和执行证据摘要、总体结果、评测器版本和必要的受限 Host 证据引用。Canary 同时包含同一案例、环境与预算下的候选和基线结果；不存在基线时明确使用无基线策略，不能伪造对照。Signoff 绑定已通过阶段和服务端固定的签署策略；签名不替代要求人工参与的策略。

执行案例通过独立的受控数据通道交付：管理员预先将冻结用例集存入受访问控制的只读存储，评测器使用其自身凭据读取仅对本次请求授权的不可变引用，读取后核对摘要。请求有效期结束后撤销读取权限；原始用例保留和删除由数据所有者按合同负责，Craft 的回执和日志只保存摘要与引用。没有安全通道时不得派发；不可把本地文件路径当成远程授权，也不可将保留集明文放在公开报告中。

Signoff 不执行案例：独立授权的签收主体签署候选、策略版本及已通过的 Shadow、Held-out 门禁摘要；此签收不可复用执行评测器的密钥。此处需要扩展现有仅支持自动签收策略的合同，旧合同不得被静默解释为新的人工签收。Canary 以固定案例逐项对照基线；无基线时暂不自动发布，直到显式定义并验证可回滚目标。

Graph 的每个阶段还须覆盖定义中的全部 Entry / Exit / Subscenario 路线。服务端从固定定义和受控案例合同生成案例到路线的映射并绑定请求摘要；评测器逐案例签署对应路线和结果，服务端验证映射不可由回执修改，按每条路线生成受信 Evidence，其 metadata 包含 `procedure_definition_digest`、`entry_id`、`exit_id`、适用时的 `subscenario_id`、`stage` 和 `status`，继续满足现有组合门禁。Signoff 不伪造运行结果，而是在签收记录明确覆盖全部路线及其已通过的前序路线证据后，为每条路线生成来源为签收的阶段 Evidence；任何路线未覆盖都不得通过。

签名算法固定为 Ed25519，编码为无填充 base64url；签名消息为 UTF-8 字节 `craft-experience-evaluation-receipt.v1`、一个零字节、随后是按 RFC 8785 规范化的 JSON 信封。公钥使用 DER SubjectPublicKeyInfo，指纹为其 SHA-256。现有 `canonicalJson` 使用本地排序规则，不能直接视作跨语言 RFC 8785 实现。解析器拒绝重复字段、未知协议、超限数据、非法编码和无法规范化的值；只保存脱敏摘要和必要引用，不保存原始提示词或密钥。实施前必须建立跨语言规范化、签名和错误输入固定测试向量。

第一版判定采用保守规则：每个必选案例及风险断言均须有明确 `passed`，缺失、重复、`not_applicable`、未知或失败都不能通过；Canary 每对案例要求候选通过且不得低于通过的基线。成本、延迟等合同指定的上限缺失时失败关闭。具体阈值必须在请求创建前由受控合同固定，不能由评测器在结果中设置。服务端复算 verdict，不能信任回执的总体 `passed` 字段。

## 6. 状态与事务

1. 创建请求时读取当前候选、评测合同、基线和活动信任策略，生成随机数及截止时间，保存不可变请求。重试必须返回相同请求，内容不同使用同一幂等键时拒绝。
2. 接收回执时严格解析并验签，再读取当前策略和候选状态。验证项目、类型、阶段、策略、签发窗口、案例集合、输入、配置摘要和基线均与请求一致。
3. 在主库 `BEGIN IMMEDIATE` 事务内重新读取调度、策略与候选版本，确认请求尚未消费且策略未撤销；发布受信证据、回执摘要、门禁和已消费状态。Experience 记录按现有存储机制先写分区、再由主库事务发布指针，原子性指主库可见性，不声称跨数据库物理提交原子。主库回滚或崩溃可能留下未发布的分区行；相同内容重试应可安全复用，不同内容冲突应拒绝，并由已有恢复机制核查孤儿行。
4. 同一请求和完全相同的回执重试返回原结果；不同回执复用请求或回执 ID 一律冲突。过期、撤销、并发结果、候选或基线漂移均不产生正向门禁。
5. 失败回执可记录并停止晋级。恢复需生成新请求，不复用旧随机数。Canary 失败保留现行版本；已发布后的回滚仍使用既有受控回滚路径。

## 7. 三仓职责与验收

Craft 负责信任策略加载、请求冻结、签名与授权验证、事务化消费和现有门禁接入；Workbench 展示评测状态、阻塞原因和证据引用，不提供普通用户自助信任公钥的入口；Eval 输出可复算的精确案例结果和来源标记，签名由独立评测器执行，模拟结果仍标记为模拟。

实现验收应包括：合法 Graph、Prompt、外部 Workflow 及四阶段正向路径；错误密钥、字段篡改、算法混淆、项目越权、无效合同、案例遗漏或重复、假通过、过期、撤销、重放、并发消费、版本和基线漂移均失败关闭；分区写入与主库指针发布之间注入崩溃，验证不可见孤儿、相同重试与不同内容冲突；跨进程撤销和消费竞争以主库提交顺序线性化，重启及旧快照恢复不能绕过撤销；主体或用例独立性不足不能晋级；Canary 回归不发布；旧报告仅供诊断。跨仓测试还需验证密钥不可由普通入口注册、私钥不进入产物，以及真实独立评测器和 Host 的部署边界。增量代码的行与分支覆盖均达到仓库要求。

交付顺序：先实现配置与只读策略校验，再实现请求冻结与回执验证，最后事务接入门禁和 Workbench 展示。每一阶段未完成时保持外部晋级关闭；不得以合成测试结果代替真实部署验收。
