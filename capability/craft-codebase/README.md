# @craft/capability-codebase

Standalone codebase kernel package. Depends on `craft-common-store-local`, `craft-common-base`, and `craft-common-log`; it does not depend on `craft-agent-harness`. Import the capability descriptor and register it with a `CraftStore` and optional `CraftTelemetry` via `CORE_KERNELS`. The existing Skill and MCP plugin remains the Host-facing surface.

`./repository-onboarding` exports `ensureRepository` and its host-neutral Workspace/checkpoint ports. Source discovery runs before the publication transaction; unchanged include paths are not rewritten. The bounded 1,200-file/12 MiB source set recognizes common source/config extensions across 30+ language families and is selected in deterministic language-family rounds, then sorted by path; omitted counts are returned by language family so a dominant language cannot silently crowd every other language out. Extension recognition means a file can enter the bounded checkpoint; it does not imply a built-in semantic analyzer or symbol/call graph for that language. The repository index policy is versioned so a selection-policy change rebuilds older snapshots. A task query prioritizes bounded file selection. `./context-search` provides ranked path/symbol candidates and explicit Chinese intent aliases. These are lexical hints, not a completeness guarantee.

Repository checkpoint source files live under `<project>/.craft_data/codebase/snapshots/<workspace>/<checkpoint>`. Project repository graph shards and adjacency routes live under `<project>/.craft_data/codebase/indexes/<workspace>/graph_records/`; project per-file analysis caches live under `<project>/.craft_data/codebase/indexes/<workspace>/analysis_cache/`. Retrieval evaluation reports are written as immutable JSON files under `<project>/.craft_data/codebase/evaluations/`. The graph manifest remains in the configured Craft data store so bounded query APIs can resolve it. `.craft_data` is excluded from repository source discovery and Git; if the project does not already ignore it, the first Codebase index adds it to that repository's private `.git/info/exclude`, without editing `.gitignore`. Existing global snapshots, graph shards and analysis caches are rebuilt into project storage the next time the repository is indexed.

Semantic repository onboarding automatically analyzes TS/JS, Python, and Java files from the immutable checkpoint. TypeScript, Python, and Java symbols retain portable declaration categories in the digest-pinned graph; analyzer schema versions change when these facts change so old file-unit caches are rebuilt. Python uses stdlib AST by default and may use Jedi when installed; Craft never installs an analyzer or executes repository code. Java uses the JDK Compiler Tree API with annotation processing disabled; it reads no project build files or external source. Resolved JDK/library symbols are excluded from the repository graph, while unresolved compiler bindings and compile errors keep the affected graph unsafe for reuse. Java caches per-file graph units without source text, invalidates changed files plus reverse call/import/inheritance dependents and same-package files, and reuses unchanged units only when bindings are complete. Javac still parses and attributes the bounded snapshot to resolve symbols, so incremental mode reduces graph extraction and persistence work rather than compiler startup or whole-snapshot attribution. Explicitly registering an LSP adapter in the user-managed `<CRAFT_DATA_DIR>/config/codebase-lsp.json` opts that language into the external semantic backend, including TS/JS or Python; it replaces that language's built-in analyzer for the selected index. Repository files cannot register or alter executable adapters. Each configured server receives a bounded temporary mirror of the selected snapshot documents, never the live repository path, and runs without a shell under the user's OS account. This is explicit executable trust, not a process sandbox. Without a matching trusted adapter, the basic index remains available and semantic diagnostics say which language lacks an adapter. The same stdio LSP client is also available for explicit analysis or normalized `craft-static-analysis-v1` imports; LSP numeric `SymbolKind` values are normalized to the same declaration category. It imports DocumentSymbol definitions and can request references, definitions, call hierarchy, implementations, type definitions, and Type Hierarchy when configured and advertised by the server. Definition requests enumerate references first and resolve at most 20 locations per symbol and 500 per request; resulting edges keep the exact reference-token span and are globally deduplicated. Type hierarchy requests are sent only for type-like LSP symbol kinds; their results are mapped to snapshot symbols and stored as static `extends` candidates. Unsupported, failed, unmappable, or over-budget relations remain explicit in diagnostics. Adapter configuration digests participate in index identity, so changes trigger re-analysis. All imported language facts pass the same `analysis_import` validation and graph budgets. Indexes store immutable, digest-checked node/edge shards plus hashed node and adjacency routes; symbol search scans node shards, while per-file symbol outlines route by checkpoint path and known-node relation, context-slice, and impact queries load only routed node/edge shards. The `craft_codebase_symbols_overview` tool returns a bounded declaration outline without source bodies; older sharded indexes retain a verified full-node fallback. Route records have per-record and aggregate byte limits. Legacy inline indexes remain readable.

Example trusted adapter registration (the executable path must exist and be executable):

```json
{
  "schema_version": 1,
  "adapters": [
    {
      "language": "cpp",
      "command": "/usr/bin/clangd",
      "args": [],
      "analyzer_version": "local",
      "relations": ["references", "calls", "implementations", "type_definitions", "type_hierarchy"],
      "max_documents": 100,
      "relation_symbol_limit": 100,
      "request_timeout_ms": 30000
    }
  ]
}
```

`request_timeout_ms` bounds each LSP request from 1 to 120,000 ms and defaults to 10,000 ms. Use a larger value for trusted servers that need time to initialize a workspace; it does not raise file, response, or graph budgets.

`relation_symbol_limit` bounds relation queries to 1–1,000 symbols and defaults to 100. The client spreads this budget across checkpoint files; when `calls` is enabled, callable declarations are considered first. A larger value can improve caller coverage on large repositories but increases LSP work, and all unqueried symbols remain reported as partial.

`craft_codebase_control_flow_query` builds a bounded, source-free, statement-level control-flow graph for an indexed TypeScript, JavaScript, Python or Java function using its digest-verified checkpoint source. It represents branches, loop conditions/back edges, returns and exceptional exits; unsupported syntax, Java `try`/`switch`/`synchronized`, Python `try`/`with`/`match`/`break`/`continue`, short-circuit expressions and syntax errors are reported as partial. It does not compute variable definitions/uses, interprocedural data flow, path feasibility, or runtime behavior. It creates no persistent source-derived graph records; its content-free receipt pins the index and source digest.

`craft_codebase_data_flow_query` accepts an indexed TypeScript, JavaScript or Python function and a variable name, then returns bounded definition/use spans and `may_reach` edges over that function's statement CFG. Definitions and uses report reachability from the function entry, so dead code after a terminal statement cannot create a flow edge. The TypeScript analyzer uses compiler symbol identity to distinguish shadowed variables; Python has one function-local binding per name and reports nested-scope, destructuring, unsupported syntax and budget gaps as `partial`. Results contain no source text and are recomputed from the digest-verified checkpoint. Neither analyzer claims interprocedural flow, taint, path feasibility or runtime behavior.

`craft_codebase_symbol_explore` is the task-oriented Agent entry point: start with a task goal, bug symptom, or code concept; a symbol name is optional. It returns the top eight bounded ranked candidates by default (maximum 10), each with static graph evidence and `relation_analysis` coverage (`analyzed`, `not_analyzed`, `partial`, or `unknown`). An empty relation list only establishes “no indexed relation” when coverage is `analyzed`; for `not_analyzed`, rebuild with semantic depth and repeat, while `partial`/`unknown` must remain inconclusive. The tool reports `exact_unique`, `exact_ambiguous`, `candidate`, `ambiguous`, or `not_found`; it never silently selects one same-named symbol and never returns source bodies. Then use `craft_codebase_symbol_read` to inspect checkpoint-bound source evidence, followed by `relations_find` or `callers_find` to continue through the graph. `definition_find` is a low-level Host adapter for an already-known path and offset, not a required Agent entry point.

For an AI-first small schema, `craft_context_tools_discover` with `intent="code"` returns the eight core Codebase navigation tools (symbol search/exploration/read/outline, callers, relations, impact and context slice). Use `intent="code-analysis"` when the task needs definition lookup, TypeScript/JavaScript/Python control flow, TypeScript/JavaScript data flow, or trusted-LSP diagnostics. Discovery only recommends schemas; it does not change Host registration. Both profiles expose read-only Codebase tools and preserve checkpoint-bound evidence.

`craft_codebase_diagnostics_find` requires an explicitly registered language server in the user-managed config. It mirrors only bounded, digest-verified files from the current checkpoint into a temporary directory, supports LSP pull diagnostics and `publishDiagnostics`, and returns findings for the requested file. The response distinguishes an empty published diagnostic set from a missing report and reports document/item omissions as partial. Diagnostic messages are included only in the live query response; receipts persist their digest and status, never the messages or source body. The configured executable remains trusted local code and is not sandboxed by Craft.

TS/JS, Python AST, and Java graph units are cached per file without source text. Repeated calls reuse a current index before invoking analyzers; modifications to existing modules recompute changed files and their known dependency closure, then reuse unaffected facts. TypeScript file-set changes, ambient/global scope, `.d.ts`, and uncertain cases fall back to a full bind. Python file-set changes, dynamic/wildcard imports, mixed analyzer versions, corrupt cache, and budget-limited output fall back to a full AST graph; Jedi output without file units also remains on the safe full path. Python and Java still parse/attribute the bounded checkpoint to resolve names; they emit/recompute graph edges only for affected units. Java file-set changes, unresolved bindings, compiler errors, mixed analyzer versions, corrupt cache, and budget-limited output trigger a full graph rebuild. Cache rows and the new index publish after snapshot validation.

`CodebaseIndexKernel.contextProjection` owns index eligibility, bounded lexical/dependency candidates, required-node completion and normalized snapshot-pinned references. `assertContextProjectionCurrent` rechecks index/workspace/activation revisions and selected file digests after Context awaits. Context consumes candidates through these SDK methods and keeps shared budget/receipt selection; it no longer reads `codebase_index` or assembles node references. Codebase remains a task projection, not an accumulated Memory/Knowledge/Experience member.
